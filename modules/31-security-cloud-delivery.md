## L3｜面试问答与连续追问

### Q1：认证、RBAC、ABAC 与对象级授权怎样组合？

**参考回答：**认证产生可信主体，RBAC 用角色表达粗粒度能力，ABAC 用主体、资源、动作及环境属性做条件判断。接口通过角色检查后仍要确认对象属于允许访问的租户或范围，例如普通用户只能读取自己的订单。查询阶段收窄范围，写入时在同一业务边界再次检查状态与权限，默认拒绝。管理员能力也应分级，避免一个全局布尔开关获得全部数据。策略变更要有版本、回归样例和可解释的拒绝日志。

**追问：异步导出按提交时权限还是执行时权限？**需先约定业务语义。敏感导出通常执行时与下载入口再检查，权限撤销后阻止发放新的访问能力；已生成文件不能公开暴露。预签名下载 URL 是临时 bearer 凭证，应用撤权不会自动撤销它，已开始的传输也未必立即停止；要求即时撤权时需要代理下载或存储层可执行的权限控制，并明确在途传输边界。

### Q2：JWT 与 Session 如何选型？JWT 怎样注销？

**参考回答：**Session 把主要会话状态放服务端，用随机标识查状态；JWT 常把声明与有效期放在签名令牌中，减少每次查会话的需要，但撤销和声明更新更困难。JWT 签名不提供内容保密，必须验证允许的算法、签名、issuer、audience、有效期及必要业务约束。注销可采用短期访问令牌加可撤销刷新会话、令牌版本或拒绝名单，代价是引入状态与查询。浏览器令牌放哪要结合 XSS、CSRF 与客户端形态，不能声称 localStorage 或 Cookie 一律安全。

**追问：密码重置后令牌怎么办？**使关联刷新会话失效；是否即时撤销访问令牌取决于威胁模型和校验机制，不能只删除前端缓存。

### Q3：OAuth、OIDC、授权码与 PKCE 分别解决什么？

**参考回答：**OAuth 解决资源访问授权，OIDC 在其上增加身份语义。授权码流程让客户端拿一次性码换令牌；PKCE 将码绑定到发起请求方生成的 verifier，降低授权码被截取后兑换的风险。回调地址要严格注册校验，state 关联发起会话以防请求伪造，OIDC 的 nonce 参与相应身份响应重放防护。ID token 是给客户端验证身份的，不能把它默认作为任意 API 的访问令牌。后端还要校验目标 API 的 audience 与权限范围。

**追问：有 PKCE 还需要客户端认证吗？**机密客户端仍按授权服务器要求认证；PKCE 不替代所有客户端身份和回调校验。

### Q4：CSRF、XSS 和 CORS 有什么关系？

**参考回答：**CSRF 利用浏览器自动携带的身份凭据，诱导用户发起有副作用请求；可结合 CSRF token、SameSite、来源校验和禁止 GET 改状态。XSS 让不可信内容进入可执行上下文，应按 HTML、属性、URL、脚本等上下文编码，富文本用可靠清洗，并辅以 CSP。CORS 决定脚本能否跨源读取响应，不是通用认证，也不能阻止所有跨源请求或 CSRF。XSS 可能代用户发请求，因而能破坏许多 CSRF 防线。

**追问：HttpOnly 能解决 XSS 吗？**它降低脚本窃取 Cookie 的风险，但恶意脚本仍可能使用当前会话执行操作；仍必须消除注入点。

### Q5：参数化查询为什么防注入？哪些地方仍有风险？

**参考回答：**参数化将 SQL 结构与值分开处理，使输入作为数据绑定。它通常不能直接绑定表名、列名、排序方向等语法位置，这些动态结构需映射到服务端白名单。ORM、MyBatis 也可能因为字符串拼接或 `${}` 插值重新引入注入。参数化不解决越权、过量返回、昂贵查询及业务条件缺失，还需行级访问条件、分页上限、超时和最小数据库权限。审计应关注所有输入通路，包括批量任务和后台管理。

**追问：只转义单引号够吗？**不够；编码、语法位置和数据库方言会改变行为，优先使用绑定参数与受控结构。

### Q6：给用户一个 URL 让服务端抓取，如何控制 SSRF？

**参考回答：**先明确允许的协议与目标范围，优先使用业务域名白名单，拒绝本地、内网、链路本地等不应访问的地址。安全校验必须涵盖 URL 解析、DNS 解析结果、重定向每一跳和实际连接目标，避免初次校验后通过重定向或 DNS 变化绕过。配合网络出口策略，禁止访问云元数据等高敏目标，限制时间、响应大小、端口与内容类型。获取页面的能力不应共享生产数据库权限。

**追问：正则检查域名后缀够吗？**不够；应按规范解析 hostname，处理国际化域名、重定向及解析地址。字符串包含公司域名并不代表目标可信。

### Q7：密码、加密、签名和哈希如何区分？

**参考回答：**密码存储应使用专为密码设计的带盐慢哈希方案，并根据实际硬件调工作因子，不能用快速 SHA-256 直接存口令。加密用密钥保护机密性，现代场景优先经过验证的认证加密；签名用于验证来源与完整性，普通哈希不能证明发送者身份。随机 token 用密码学安全随机数。密钥放受控管理服务，按用途、环境隔离并支持轮换；日志和错误响应不暴露明文、私钥和完整令牌。

**追问：加盐后为何还要慢？**盐抵抗预计算与相同密码关联；慢哈希增加离线猜测单次成本，两者解决不同问题。

### Q8：如何处理日志、隐私删除与审计之间的冲突？

**参考回答：**先做数据分类和最小收集，把业务标识、身份信息、密钥分开。日志应默认脱敏，访问受限并有保存期限；审计记录关键主体、动作、对象、结果、关联 ID 和可信时间，防止普通业务权限篡改。删除流程要追踪主库、索引、缓存、对象存储、训练/评测数据与备份恢复后的处理规则。保存义务和删除要求由组织规则确定，工程上提供可验证的数据流与策略执行证据。

**追问：哈希手机号算匿名吗？**未必；低熵空间可枚举，且关联数据可能重新识别。不要把“看不见原文”等同不可识别。

### Q9：依赖扫描、SBOM、构建可复现分别有什么用？

**参考回答：**依赖扫描帮助识别已知漏洞，SBOM 记录产物中包含哪些组件，可复现构建与产物签名帮助追溯来源和验证完整性。它们不能直接证明业务没有漏洞。流水线应固定依赖版本、控制仓库来源、审核构建脚本权限，隔离不可信 PR 的密钥权限，并把漏洞影响与实际可达性、修复成本一起评估。部署应使用已验证的同一产物，避免每个环境重新打包得到不同内容。

**追问：发现高危依赖就立刻升级全部服务吗？**先确认暴露路径并控制风险，验证兼容性与回归；紧急缓解和长期修复可并行，不能只改扫描报告。

### Q10：单元、集成、契约、端到端测试怎样分工？

**参考回答：**单元测试验证局部规则与边界，集成测试覆盖真实存储、事务与框架行为，契约测试约束服务接口兼容，端到端测试验证关键用户流程。越靠外成本和不确定性通常越高，因此关键规则用大量快速确定性测试承接，少量代表性全链路测试补边界。Mock 适合隔离外部故障，但不能证明数据库隔离、SQL 方言或消息语义。测试需要明确断言业务不变量，避免只验证调用过某方法。

**追问：线上 bug 已修，怎样防回归？**把导致错误的最小条件固化在最靠近根因的稳定测试层，并补必要的边界集成证据。

### Q11：容器与虚拟机的隔离区别是什么？

**参考回答：**常见 Linux 容器共享宿主内核，用 namespaces 隔离可见资源，用 cgroups 计量和限制资源，镜像提供用户空间文件系统。虚拟机通常有独立来宾内核和虚拟硬件边界。容器启动快不代表默认隔离等同虚拟机；特权模式、宿主目录挂载和过宽 capability 会扩大风险。镜像应最小化、非 root、只读根文件系统按需开放写目录，同时控制网络和凭据范围。

**追问：容器里看到 8 核就能开 8 倍线程吗？**还要看 CPU quota、cpuset、JDK 容器感知与任务特性；宿主核数和可持续 CPU 配额不是同一概念。

### Q12：Deployment、StatefulSet、Service、Ingress 怎样分工？

**参考回答：**Deployment 管理通常可替换的无状态副本和滚动更新；StatefulSet 提供稳定身份及相关存储关联，适合需要这些语义的工作负载，但不会替数据库实现共识和备份。Service 提供到一组后端的稳定访问抽象；Ingress 描述 HTTP 路由，需要实际控制器实现。Pod 是调度单元，其中多个容器共享部分资源边界。把应用放入集群后仍要设计数据库故障域、升级顺序和持久卷恢复。

**追问：有三个数据库 Pod 就高可用了吗？**副本数不能替代正确复制协议、仲裁、故障域与运维流程，三个 Pod 在同一故障域仍可能一起失效。

### Q13：存活、就绪、启动探针怎样避免故障放大？

**参考回答：**启动探针允许慢启动在预算内完成；就绪探针控制实例是否应承接服务流量；存活探针用于发现需要重启才能恢复的失活。不要把所有下游可用性都塞进存活探针，否则数据库抖动会触发全应用重启。就绪判定也要避免瞬时故障导致所有副本频繁摘挂。阈值、周期与超时应结合启动时间、抖动和故障恢复目标设置，探针本身必须轻量。

**追问：HTTP 返回 200 就一定健康吗？**只能说明该检查通过；应区分进程可运行、能接新请求、关键业务可完成三种信号。

### Q14：requests、limits 与 OOMKilled、CPU throttling 的关系？

**参考回答：**requests 影响调度与资源分配预期，limits 约束使用上限；CPU 超限可能被节流，内存压力可能导致容器进程被终止。应用 JVM 堆只是进程内存的一部分，线程栈、元空间、直接内存、代码缓存和本地库都占空间，因此 Xmx 等于容器内存上限通常不合理。定位时结合容器事件、内存曲线、cgroup 指标、RSS 和 JVM 指标，区分 Java 堆 OOM 与容器被杀。

**追问：CPU 平均 40% 为什么还超时？**平均值可能掩盖短时节流、单热点线程和节点争用；检查采样窗口、quota 与请求时间线。

### Q15：HPA 扩容为什么有时救不了系统？

**参考回答：**弹性有观测、决策、调度、启动与预热延迟，无法替代限流和容量余量。CPU 低而数据库连接池满时，按 CPU 扩容可能不触发；盲目扩应用副本还会增加下游连接和重试。指标应与瓶颈匹配，例如积压年龄、并发或处理速率，设置最大副本、稳定窗口与依赖预算。突发流量可预扩容与分级降级，结合压测验证整个链路的可扩展上限。

**追问：队列长度下降是否说明扩容有效？**还要看吞吐、积压年龄、失败率及消费后业务完成率，丢弃任务也会让队列变短。

### Q16：滚动、蓝绿、灰度发布怎样选？

**参考回答：**滚动逐步替换副本，资源额外成本相对可控；蓝绿准备两套环境后切流，回切快但需要额外容量和数据兼容；灰度将一部分有代表性的流量交给新版本，用指标决定扩量或回滚。灰度必须覆盖关键租户、地区与接口，单看平均错误率容易漏掉小群体损坏。每种方式都要考虑后台任务、消息消费者、缓存和数据库 schema，新旧版本共存时接口与数据格式必须兼容。

**追问：新版本写了旧版本看不懂的数据，回滚能救吗？**未必；发布前应采用兼容写入与分阶段切换，回滚条件必须包含数据状态。

### Q17：Java 服务怎样优雅退出？

**参考回答：**先停止接受新工作并让流量摘除传播，继续处理有预算的在途请求；停止拉取新消息，完成或释放当前任务，正确处理提交位点；关闭线程池、刷新必要状态，最后结束进程。平台终止宽限时间必须覆盖传播、排空与清理，仍要接受强制终止可能发生，因此业务应幂等且可恢复。HTTP 请求结束不代表异步副作用完成，要单独记录任务状态。

**追问：sleep 30 秒就优雅了吗？**固定等待没有证明工作完成；需要在途计数、取消传播和明确截止时间，并监控退出超时率。

### Q18：数据库迁移为什么推荐 expand/contract？

**参考回答：**先增加兼容字段或表，使旧程序仍可工作；再部署能兼容新旧数据的代码，按主键分批回填并对账；确认读路径切换、观察期和回滚窗口后，才删除旧字段。双写要定义唯一事实来源和修复逻辑，避免两个字段永久分叉。大表变更还需评估元数据锁、在线 DDL 条件、复制延迟和磁盘占用。每一步都应该能暂停，而不是把所有操作压成一次不可逆发布。

**追问：回填时有并发更新怎么办？**用版本条件、更新时间水位或持续变更流补齐，再对账；盲目覆盖会把新值写回旧值。

### Q19：备份、RPO、RTO 和灾备演练怎样回答？

**参考回答：**RPO 描述最多可接受的数据损失时间范围，RTO 描述恢复服务的目标时间。复制不能替代备份，因为误删和损坏可能同步传播；备份文件存在也不代表能在目标时间恢复。设计应包含全量与增量、密钥、配置、依赖顺序、异地副本和定期恢复演练。演练记录实际恢复时间、数据校验、流量切换及切回，识别人员与流程依赖。

**追问：宣称零数据损失需要什么证据？**说明故障模型、提交确认与复制持久化条件，并用演练验证；不能把正常复制延迟小当作所有故障都零损失。

### Q20：一次发布需要哪些“可交付”的证据？

**参考回答：**从需求验收条件开始，给出关键规则测试、变更影响、产物版本与来源、兼容性、容量和故障行为，明确观测面板、分批放量条件及回滚入口。涉及权限和数据迁移时增加针对性验证，而不是套所有项目相同清单。上线后对比相同流量分层下的业务成功率、错误和延迟，保留关联版本与操作审计。完成标准是用户目标满足且风险在约定范围内，不是流水线绿灯本身。

**追问：如何衡量交付效率？**结合变更前置时间、部署频率、失败与恢复、用户价值，不能单独追求提交数或发布次数。

## L4｜演练与过关

1. 给“跨租户导出订单”的接口写允许/拒绝矩阵，覆盖读、写、批量、异步、下载、权限撤销；用测试证明越权失败。
2. 画新旧版本共存时间线：新增 `amount_minor`，回填、对账、切读、收缩；列出每一步能否回滚及原因。
3. 推演数据库抖动、探针全红、扩容、连接总数上升的放大链，给出止损顺序。

**过关标准：**能用资源边界解释安全问题，用兼容性与业务不变量解释发布风险；10 分钟内列出一个实际服务的退出/恢复流程，并指出至少三个失败窗口。将练习结果记入 [复习记录](../practice/review-template.md)。
