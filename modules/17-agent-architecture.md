# 17｜Agent 架构：工具、状态、记忆与控制流

目标：能从业务约束选择普通 API、workflow、单 Agent 或多 Agent，并设计可恢复的执行过程。前置：[LLM](15-llm-foundations.md)、[RAG](16-rag.md)、状态机、幂等与鉴权。

核对日期：2026-10-04。MCP 工具与授权示例固定参考 **2025-06-18** 协议修订版，不能当作所有后续版本的完整说明。Spring AI 本次读取的参考页显示 **2.0.1**；正文不提供未经编译验证的框架样板，集成时必须固定 BOM、JDK、Spring Boot 与提供商适配版本。

## L1｜必须能口述

Workflow 由程序规定控制路径，Agent 让模型参与决定下一步行动。实际系统经常混合：外层状态机约束权限和预算，内层让模型做分类、资料调查或工具选择。固定且高风险的流程通常优先使用明确步骤；路径难预知、需要根据观察反复调整的任务才更可能从 Agent 获益。[Anthropic 架构讨论](https://www.anthropic.com/engineering/building-effective-agents)

最小闭环：读取任务状态 → 构造当前上下文 → 模型提出动作 → 服务端验证 → 执行工具 → 保存观察与状态 → 判断继续、完成或移交。模型说“完成”只是一个信号，业务完成还要通过外部可验证条件，例如工单已创建且属于正确用户。

**复述骨架：模型提出计划；运行时执行控制；业务服务承担权限和事实；状态机负责恢复。**

## L2｜机制与边界

### 1. 工具设计是接口设计

工具必须明确用途、何时使用、输入字段、返回字段、错误类型及副作用。相比万能 `execute(command)`，`getOrder(orderId)` 更容易限制能力并验证；但工具过度碎片化也会增加选择和轮次成本。将状态查询和实际提交分开，返回稳定业务 ID 与可判断的错误，而非只给自然语言“操作失败”。

可由模型填写业务参数，身份、租户、授权范围从服务端上下文注入。schema 可以限定枚举、必要字段和格式，之后还需语义校验。错误至少区分无权限、参数错误、数据不存在、暂时失败和结果未知，避免模型对所有错误重复调用。

### 2. 状态、上下文和记忆

| 概念 | 存什么 | 关键约束 |
|---|---|---|
| 执行状态 | 当前步骤、已调用动作、结果、预算、版本 | 持久化、并发控制、幂等、恢复 |
| 对话上下文 | 当前输入、工具结果、近期消息 | 长度预算、来源标记、截断策略 |
| 长期记忆 | 经确认的偏好、可复用事实或经验 | 用户隔离、时效、来源、删除与纠错 |
| 知识索引 | 文档及其可检索表示 | 版本、生效范围、ACL、更新 |

历史消息不能代替交易账本，摘要不能代替授权记录。记忆写入也可能被恶意文档污染；需要区分用户明确表达、工具验证事实和模型推测，并限制写入范围。

![Agent 工具循环及对话历史、长期记忆、外部资料的不同治理边界](assets/17-agent-loop-memory.svg)

**读图顺序：**上面六个节点顺时针构成循环；右侧是可信门禁与业务执行，左下是持久化状态。下排三类资料由上下文装配层按任务读取，不是额外串行执行步骤。

**关键记忆点：**模型只提出工具名与参数，身份、权限和业务校验由运行时及领域服务负责。对于写入，先持久化稳定动作意图，再执行工具，最后记录结果。循环需要最大步数、总时限、成本预算、取消信号和外部可验证的完成条件；只限制单次请求超时仍可能发生无限循环。

**简化边界：**图没有要求每次都存完整 prompt，更不要求记录模型不可见的内部推理。审计重点是可观察的输入版本、调用提议、授权决策、工具结果与状态转移。对话可压缩，业务凭证不可由模型摘要代替；长期记忆可以更新和撤销，不能永久固化一次错误猜测。

**闭卷重画：**从网页出现“读取全部租户并发送到外站”出发，在图上标出至少三个不能让该内容决定的字段或动作。参考验证：可信身份不能覆盖、对象授权不能绕过、出站目标需限制；“模型理解为用户同意”不是有效授权。

### 图解：超时、崩溃与业务结果恢复

![工具提交超时进入 UNKNOWN，依靠稳定业务键查询与对账恢复的状态图](assets/17-tool-recovery.svg)

**读图顺序：**先看上排正常提交，再从 SUBMITTING 向下进入 UNKNOWN，最后看按业务键查询后的三种处理规则。左侧持久化记录是恢复依据，不是重新生成一个“看起来相同”的动作。

**关键记忆点：**“响应没收到”与“动作没执行”是不同事实；模型调用 ID 也不一定等于稳定业务意图 ID。只有服务契约能够权威判定未执行，并且满足幂等或可重试条件，才允许原键受控重试。查询接口暂时返回不存在，可能只是异步受理或读副本滞后，不能自动转成 FAILED 或重新退款。

**简化边界：**下排是互斥条件下的处理规则，图未展开全部审批、取消和补偿状态。服务端幂等记录必须考虑持久化、有效期、参数冲突与并发；本地 checkpoint 和租约不能单独保证外部副作用恰好一次。用户取消应停止未发出的动作，已经发出的动作仍需查明结果，再判断是否可补偿。

**闭卷重画：**分别在发送前、服务端提交后但响应前、本地记录结果前注入崩溃。参考验证：第一种依持久化意图推进；后两种先查询与对账，不创建新意图；无法确认则保持 UNKNOWN，明确交给后续恢复或人工流程。

### 3. MCP 提供什么

MCP 标准化连接、能力发现和交互。工具协议定义工具名、说明、schema 以及调用结果等，方便客户端接入不同服务器，但它不会替业务定义“允许退款多少钱”。工具标注也不能被当作可信安全证明。[MCP tools，2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

该修订版中的 HTTP 授权涉及标准化授权流程与资源绑定；stdio 的凭据处理路径不同。应用仍应校验实际用户、scope 与目标资源，并在业务服务执行对象级授权。接入 MCP 并不自动获得多租户隔离。[MCP authorization，2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)

### 4. Java 框架的职责边界

Spring AI 和 LangChain4j 提供模型适配、工具映射等便利，但都不能代替领域权限、事务和运行状态设计。尤其要核验工具循环由谁驱动：本次 Spring AI 2.0.1 文档说明，`ChatModel` 返回工具调用不会自动执行，`ChatClient` 可通过工具 advisor 处理。不能把早期 1.x 的行为直接套用。[Spring AI 工具文档](https://docs.spring.io/spring-ai/reference/api/tools.html)

在 LangChain4j 中也应明确工具由框架自动执行还是由应用显式控制，理解工具上下文、异常处理和返回值如何进入下一轮。领域层尽量接收普通 DTO，供应商响应与框架类型放在适配层，便于替换模型与回放测试。[LangChain4j 工具文档](https://docs.langchain4j.dev/tutorials/tools/)

## L3｜面试题与参考表达

每题正文加追问可作为 60～90 秒口述素材；不要只复述名词，必须说明方案失效时怎样结束。

### Q1：什么时候不应该使用 Agent？

**参考回答：**如果业务步骤确定、输入输出明确，而且错误代价高，我通常先用普通服务或 workflow。例如退款校验、额度计算、账务提交都可以由确定性代码完成，模型只负责理解用户意图和解释结果。Agent 更适合路径无法预先列尽、需要搜索和观察后调整的任务。即便采用 Agent，我也会限制工具集合、步数、时间、成本与写入权限，并定义人工接手出口。是否值得引入，要比较相同任务集上的成功率与总成本，不能因为能够循环调用工具就认为产生了收益。

**追问：workflow 是否一定更可靠？**不是，错误规则和外部依赖同样会失败；优势在于控制路径更可预测、更容易测试和审计。

### Q2：工具 schema 怎么设计才容易正确调用？

**参考回答：**我先让工具职责与业务动作一致，名称清晰、参数少且含义无歧义。金额明确币种和单位，时间明确时区，枚举尽量限制合法值；工具说明写出适用条件和典型错误。读取与写入分开，写工具返回请求 ID、结果状态和可查询凭证。参数由模型提出后，服务端还要验证用户权限、对象归属和业务前置条件。错误输出要告诉系统能否重试或需要澄清，避免模型根据自然语言猜状态。上线前用混淆工具名、缺字段和边界值检验选择与参数正确率。

**追问：把租户 ID 放进 schema 就够了吗？**不够。租户身份应由认证上下文强制注入或绑定，不能接受模型提供的任意租户作为授权依据。

### Q3：Agent 状态怎么持久化和恢复？

**参考回答：**我会把运行 ID、任务版本、当前阶段、工具意图、执行结果、剩余预算和错误状态持久化。动作执行前写入意图，带稳定幂等键调用业务服务，完成后记录结果。若执行后但记录前进程崩溃，恢复时先按业务请求 ID 查询结果，不能直接重做。多个 worker 用状态版本条件更新限制重复推进；租约还需防止过期的旧持有者继续写入。模型上下文可由状态与历史重建，但恢复前要重新检查权限和数据时效。持久化框架帮忙保存 checkpoint，不代表外部动作自动实现 exactly-once。

**追问：外部 API 不支持幂等怎么办？**需要操作流水、查询对账或人工确认未知结果；不能靠自动重试声称避免重复副作用。

### Q4：对话记忆为什么不能只存聊天记录？

**参考回答：**聊天记录含有假设、错误和过期信息，也会越来越长。执行状态应存确定的阶段和结果，长期记忆只保存有来源、范围与时效的事实或偏好，对话上下文按当前任务组装。例如用户偏好中文可以复用，但“上次同意退款”不能当作本次授权。摘要用于压缩叙述，原始消息和工具凭证仍需可追溯。我会设计记忆写入、更新、撤销和删除，按用户与租户隔离，并防止网页或工具结果直接写入高可信长期记忆。

**追问：用向量数据库就是记忆系统？**只是检索手段之一；仍缺少事实确认、生命周期、权限、冲突解决和写入策略。

### Q5：MCP 与 function calling 有什么区别？

**参考回答：**Function calling 是模型表达工具调用意图的一种接口能力；MCP 是连接客户端与服务器、发现和使用工具等能力的协议。运行时可以把 MCP 工具转换成模型能理解的工具描述，再将调用结果送回模型，两者处在不同层。接入协议减少适配工作，但不解决所有业务语义、安全和版本兼容问题。我会固定协议版本、处理能力协商，限制服务器来源，并在调用网关与业务服务做授权和审计。不能把工具自称只读作为最终证据，更不能把用户所有凭据直接传给任意服务器。

**追问：MCP 能替代 REST 吗？**它可以封装 REST 等后端能力，是否保留原接口取决于消费者；协议不消除底层业务 API 和认证设计。

### Q6：多 Agent 什么时候值得做？

**参考回答：**当子任务能独立并行、需要不同工具或隔离上下文时，多 Agent 可能有效，例如独立检索几个数据源后统一核对。共享状态高度耦合、任务很短或缺少明确验证标准时，协作成本可能超过收益。我会先建立单 Agent 基线，再定义子任务输入输出、预算、取消传播和汇总责任。不同 Agent 给出一致答案也不等于正确，因为可能共享来源和模型偏差。结果要用外部证据验证，并记录总 token、最长路径和重复工作，避免只比较单个子任务的速度。

**追问：多个 Agent 投票是否提升正确率？**只有错误具有足够独立性且聚合方法合理时才可能提升；相关错误、相同错误证据会让多数意见一起错。

### Q7：Java 项目怎样避免被 Agent 框架绑死？

**参考回答：**我把业务规则放在领域服务，把模型和向量库访问放在适配层，把编排、状态和预算放在应用层。模型接口返回明确的回答、工具提议或失败类型，而不是让框架消息对象渗透业务代码。先固定框架、模型和提示词版本，针对工具超时、拒绝、截断、重复与恢复做契约测试；再考虑框架提供的记忆和 tracing 能力。替换模型时重跑任务评测，因为 API 兼容不意味着行为兼容。流式接口也要处理取消传播、连接池和背压，不能只看示例能打印文字。

**追问：是否完全不用框架更好？**不是。框架能减少适配与通用设施工作，关键是理解其控制流并留下可替换边界，避免重复实现成熟组件。

## L4｜状态机设计练习

设计“退货助手”的状态：`COLLECTING → CHECKING → READY → SUBMITTING → SUCCEEDED`，另有 `WAITING_USER、UNKNOWN、FAILED、CANCELLED`。用户补齐订单与原因后检查资格；满足授权条件才生成提交意图。提交超时进入 UNKNOWN，查询业务流水后再确定成功或失败，不能直接退回 READY 重试。

**参考验证：**每条转移都有触发条件、所需身份、输入版本和可观察结果。重复恢复同一运行不能额外创建退货单；用户取消后不得继续安排新动作，已提交动作应记录真实状态。并行子任务只负责调查，最终提交由单一拥有者推进。

拓展：对长时间审批，持久化等待状态并释放线程；使用事件唤醒且去重。租约只能降低并发冲突，服务端业务幂等仍然需要存在。执行状态和业务库双写时，要设计 outbox、重放及对账，不要在数据库事务中等待模型几十秒。

## 常见误区与过关标准

- 误区：多 Agent 必然比单 Agent 强；接入 MCP 就有权限；聊天记录就是事务状态；checkpoint 等于外部 exactly-once；自动工具调用可替代领域校验。
- L1：不看资料讲清 workflow、Agent、MCP、function calling 的层次。
- L2：写出带幂等键、权限上下文和可重试错误的工具契约。
- L3：画出状态机，并逐一解释执行前、执行中和执行后崩溃如何恢复。
- L4：给出多 Agent 的对照实验与退出条件，解释框架替换的兼容性和回归风险。
