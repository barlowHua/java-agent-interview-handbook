# 30｜代码设计、设计模式与领域建模

优先级 P0/P1。前置：01、05、09、19。目标不是背 23 个模式名称，而是把变化点、状态不变量、依赖方向和协作边界讲清楚。本章是原创情境式训练；术语以具体代码和约束解释，不把一种流派当唯一正确架构。

## L1 从职责和变化出发

好的模块在内部消化复杂规则，对外提供清晰契约。代码行数少不一定易维护：一个万能接口若要求调用方知道所有细节，复杂度只是被转移了。先明确输入、输出、错误、副作用和不变量，再决定接口和类。

## L3 核心问答

### Q1：SOLID 怎么应用，怎样避免教条？

**参考回答：**单一职责强调围绕变化原因组织模块；开闭原则关注稳定契约下扩展；里氏替换要求子类型不破坏使用方假设；接口隔离减少不相关依赖；依赖倒置让策略不绑死细节。它们是分析工具，不是让每个类都加接口。评估时看修改传播、测试难度和调用方认知负担，而非接口数量。

**追问：只有一个实现还要接口吗？** 若确有隔离外部依赖或替换测试的需要可以；否则增加抽象可能只有导航成本。

### Q2：组合与继承如何选择？

**参考回答：**继承表达可替换的类型关系，同时把子类绑定到父类行为；组合把能力交给协作者，更容易独立替换。若只是复用几行代码而没有稳定的 is-a 契约，组合通常更易控制变化。父类新增回调或改变内部调用顺序可能破坏子类，因此要考虑行为兼容，不只看方法签名是否一致。

**追问：装饰器是不是继承？** 它通常实现相同接口并持有被装饰对象，用组合叠加行为；具体语言实现可以结合继承，但机制不能混淆。

### Q3：策略模式和模板方法有什么区别？

**参考回答：**策略将可替换算法封装成协作者，运行时可以选择；模板方法把流程骨架放在基类，通过扩展点定制局部步骤。若变化维度多，继承组合容易爆炸，策略更灵活；流程必须统一且扩展点少时模板也可用。设计时要说明谁选择策略、非法组合如何拒绝、公共错误处理放在哪里。

**追问：什么时候只是 switch 就够？** 规则少、稳定、局部且没有独立演进需求时，清晰 switch 可能更合适，不必预先构建插件系统。

### Q4：工厂、建造者和依赖注入各管什么？

**参考回答：**工厂封装实例创建与选择，建造者适合逐步组织较复杂的构造参数，依赖注入将对象的依赖由外部提供。三者可以共存，不是同义词。构造完成时应保证对象有效，避免 builder 产生缺少必要字段的半成品。DI 容器帮助装配，但不会自动划分业务职责或验证领域不变量。

**追问：大量可选参数一定用 Builder？** 先看参数是否属于同一概念；可能应拆成几个值对象，而不是让一个巨型构造器换个外观。

### Q5：代理、装饰器、适配器、门面怎样区分？

**参考回答：**代理控制访问或附加调用拦截，装饰器在相同抽象上叠加能力，适配器转换不兼容接口，门面为复杂子系统提供更聚焦入口。它们外形可能都是“包一层”，差别在意图与契约。Spring 事务代理关注调用边界，第三方 SDK 适配器关注模型与错误转换，不能只按类结构判断模式。

**追问：包一层 SDK 就隔离成功了吗？** 如果供应商 DTO、异常和生命周期仍泄漏给业务，变化仍会穿透，应检查调用方是否真正依赖稳定契约。

### Q6：观察者和事件总线会带来什么代价？

**参考回答：**事件可以降低发布方对订阅者的直接依赖，但控制流变得不直观，错误、执行顺序和事务边界需要明确。同步事件可能在发布线程阻塞并影响事务；异步事件需要讨论投递、重试、幂等和恢复。不能因为用了事件名就把进程内回调当可靠消息，也不能靠隐式监听器完成必须原子提交的关键规则。

**追问：事务提交后发事件就不会丢吗？** 数据提交与发布之间仍有崩溃窗口，可靠异步需 Outbox 等持久化协议。

### Q7：责任链适合什么，不适合什么？

**参考回答：**适合由多个独立处理器按规则协作的流程，如认证、参数校验和转换。要明确定义是否短路、顺序、上下文修改和异常传播。如果步骤之间有复杂状态和补偿依赖，单纯链式调用可能掩盖业务流程，显式状态机更易恢复。链越长越需要观测每个处理器耗时与结果。

**追问：处理器顺序配置错了怎么办？** 把安全前置关系变成装配验证或明确代码契约，并测试绕过与顺序反例，不只依赖文档。

### Q8：实体和值对象如何区分？

**参考回答：**实体用持续身份表示同一个业务对象，即使属性变化仍是它；值对象以值与规则表达概念，如金额、地址快照或时间区间。分类取决于业务语义，不能按有没有数据库主键机械判断。值对象适合不可变和构造校验，实体承担状态转换。持久化 DTO 与领域对象可一致也可分离，取决于复杂度与边界。

**追问：地址永远是值对象吗？** 订单中的配送地址快照常按值处理；地址管理系统可能有独立地址实体，需要看身份与生命周期。

### Q9：聚合为什么不是随意把关联表放在一起？

**参考回答：**聚合围绕需要一起维护的不变量划定一致性边界，由根控制合法变化。把大量关联对象都纳入一个聚合会增加锁范围、加载成本和冲突；切得过细又可能把必须原子的规则拆开。先列不变量，再结合事务与竞争设计大小，而不是照数据库外键画聚合。

**追问：跨聚合规则怎么处理？** 根据业务要求用应用编排、本地或分布式事务、预约或事件后对账，明确不一致窗口与失败出口。

### Q10：领域服务和应用服务怎么划分？

**参考回答：**应用服务组织一个用例，处理身份、事务和外部协作；领域对象或领域服务表达业务规则。无自然归属的领域规则可以进领域服务，但不能把所有逻辑搬进一个万能 service。判断标准是：规则是否随业务变化、能否脱离 HTTP/数据库框架解释和测试。简单 CRUD 没必要为了分层复制一堆相同 DTO。

**追问：校验都放领域层吗？** 传输格式校验在边界，权限和对象业务约束按其职责落实；重复保护关键不变量是有意义的，但不要无差别复制所有校验。

### Q11：限界上下文与微服务是一回事吗？

**参考回答：**限界上下文约束一套模型与语言的适用范围，微服务是部署和运行边界。一个上下文可以先作为单体中的模块，多个服务也不一定形成清晰模型。订单、账务、履约可能对“已完成”有不同定义，应明确映射与接口契约。先划清业务语义，再依据团队、独立扩展与发布需求决定部署拆分。

**追问：共享数据库能否仍有边界？** 可以有逻辑边界，但直接跨模块改表容易绕过契约，应限制所有权并建立验证。

### Q12：防腐层解决什么问题？

**参考回答：**它在外部模型与本地业务模型之间转换语义、错误和交互协议，减少外部系统变化对内部规则的污染。例如第三方支付状态需要映射为自己的状态机，并保留原始结果用于审计，而不是把供应商字符串遍布代码。它有维护成本，应围绕真正不稳定或语义不同的边界设置。

**追问：翻译字段名就够了吗？** 不够，还包括状态语义、幂等约定、超时后的不确定结果和恢复方法。

### Q13：状态机比多个布尔字段好在哪里？

**参考回答：**多个布尔值容易形成业务不允许的组合，状态机显式列出状态、事件、守卫、转移和动作。例如订单付款后取消需要退款流程，不能直接把 cancelled 设为 true。持久化状态还需版本或条件更新防并发越界，外部动作需要幂等和恢复。状态机提高可推理性，但不会自动提供分布式事务。

**追问：状态爆炸怎么办？** 分清独立维度，如支付与履约，分别建模再定义协调规则，避免把所有组合压成一个巨型枚举。

### Q14：CQRS 一定要两套数据库吗？

**参考回答：**CQRS 的核心是区分读写模型或职责，不必立即使用两个物理存储。查询模型可以针对展示优化，写模型维护不变量；若异步生成读模型，就增加延迟、重建和一致性问题。简单系统可以先用同库不同服务接口，只有明确读写需求差异才承担额外同步成本。

**追问：用户刚写完却查不到怎么办？** 设计读己之写策略，如返回写结果、版本等待或临时从权威写侧查询，并明确超时出口。

### Q15：Event Sourcing 与普通审计日志有什么区别？

**参考回答：**事件溯源以事件序列作为状态来源，通过重放得到状态；审计日志通常只是当前状态之外的记录。事件溯源要求事件语义稳定、版本兼容、顺序与重建正确，快照仅加速恢复。外部副作用不能在重放时重复执行。业务确需历史重建和事件模型时才考虑，否则复杂性可能超过收益。

**追问：修复错误事件就删除它吗？** 要按业务与审计要求使用纠正事件、版本迁移或受控修复，不能随意破坏历史解释。

### Q16：幂等键应该放在什么模型里？

**参考回答：**它应绑定业务操作身份与作用域，而不是每次 HTTP 请求的新 UUID。模型通常包含主体、操作类型、键、参数摘要、执行状态和结果。相同键不同参数必须识别冲突，记录保留期覆盖重试与回放。用它协调外部副作用时，还需下游提供稳定键和结果查询，本地唯一约束不能控制远端已经做了什么。

**追问：key 放缓存过期后可以重做吗？** 不一定，要看业务可接受重放窗口和持久唯一约束，重要效果通常需要更长期证据。

### Q17：如何重构一个上千行的 Service？

**参考回答：**先识别用例与业务不变量，补充关键行为证据，再把纯规则、外部适配与流程编排逐步分离。按调用方契约小步替换并比较结果，不先按技术名词大规模搬文件。每一步明确异常、副作用、事务范围与顺序是否变化。重构收益用变更影响、缺陷和测试可维护性观察，而不只看类变短。

**追问：没有测试怎么办？** 从关键输入输出与故障边界建立特征测试和受控对照，必要时影子读验证，避免重复写副作用。

### Q18：接口兼容只要不删字段就行吗？

**参考回答：**兼容包括语法和语义：新增枚举、默认值变化、精度、错误码、排序、空值和超时都可能破坏调用方。协议应明确必需字段与容错规则，用消费者契约测试和灰度观测验证。版本升级要考虑新旧同时运行，不能假设所有调用方同一天升级。

**追问：金额单位从元改分但字段名不变？** 语法不变而语义破坏，必须用明确版本或新字段迁移，避免静默产生错误。

### Q19：怎样区分领域事件、集成事件和技术事件？

**参考回答：**领域事件表达业务上发生的事实；集成事件是跨边界发布的稳定契约；技术事件描述缓存失效、线程完成等机制。内部模型变化不应直接迫使所有外部消费者升级，因此集成事件需要版本、身份、时间语义与必要字段。命名最好描述已发生事实，并区分命令请求与结果事件。

**追问：事件里带整个数据库实体好吗？** 通常会泄漏内部字段和变化，宜按消费者语义设计最小稳定载荷，并考虑重放与权限。

### Q20：设计评审时你优先问哪几件事？

**参考回答：**先问目标和不变量，再问失败时谁知道结果、谁恢复、多久恢复；接着看数据所有权、并发与权限边界，最后评估容量、观测和迁移。可逆性和运维成本与功能同样重要。对每个复杂组件要求说明它解决哪个已证实问题，并给出更简单方案为何不够，而不是凭熟悉程度选技术。

**追问：需求还不确定怎么办？** 保留少量明确扩展边界，先验证核心流程与风险最大的假设，避免为所有想象中的未来提前建设。
