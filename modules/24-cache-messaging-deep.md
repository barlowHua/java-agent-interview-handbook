## L1—L3 · Redis：12 个深入问题

### Q1：Redis 的逻辑类型与底层编码为什么不能混为一谈？

**参考回答：**类型决定命令语义，编码决定相同语义如何在内存实现。小对象常采用紧凑编码节省指针和分配开销，规模或元素大小越过阈值后可能转换为更适合查询更新的结构。因此不能把所有 Hash 都当哈希表、所有 Sorted Set 都当跳表，也不能把一个历史版本的阈值背成永久常量。编码变化可能突然改变内存和操作成本，测试应覆盖阈值附近、真实键长和值长。设计先从访问模式、返回量和生命周期选择类型，再用目标版本的 OBJECT ENCODING、内存统计与延迟测量验证，而不是依赖类型名称估算容量。

**深入追问与答案要点：**一百万个小 Hash 与一个百万字段 Hash 占用相同吗？不会简单相同；顶层键、过期、对象头、编码和访问粒度都不同，还会影响热点与迁移。

### Q2：哈希表扩容与渐进式 rehash 解决了什么，又没解决什么？

**参考回答：**哈希结构依靠桶定位和冲突处理提供常见的快速查找，但负载变化需要扩缩容和迁移条目。渐进式 rehash 把迁移工作分摊到后续操作或周期工作，避免把所有元素一次性搬完造成长暂停；过渡期可能同时存在新旧表并增加内存。它不意味着每条命令成本完全恒定，也不消除大 key、分配器、fork 或异常冲突分布的延迟。排查时需要看对象规模、编码和服务器整体资源，不能因为平均复杂度低就认定无法成为热点。源码学习应跟踪查找、插入与迁移如何同时访问新旧表。

**深入追问与答案要点：**为什么背景持久化时要关注 rehash？迁移和修改内存可能增加写时复制压力；具体暂停或推进策略随版本实现核对，不能声称任何版本都完全停止所有扩缩容。

### Q3：Sorted Set 为什么常结合字典和跳表？

**参考回答：**排行榜同时要求按成员快速查询分数，以及按分数排序、取名次和做范围扫描，单一哈希结构不擅长有序范围。较大编码下结合字典与跳表，可以分别服务成员定位和有序访问；跳表通过多层链接缩短定位路径，底层保留有序遍历。小规模紧凑编码则可能更省空间。复杂度还要包括返回的元素数量，查前十与返回几十万条不能视为相同负载。分数相同有明确决胜排序，若业务要求同分并列名次或按另一时间字段排序，需要额外设计，不能直接套 Redis 的排名当业务名次。

**深入追问与答案要点：**把时间戳拼进 double 分数总安全吗？需考虑浮点精度、数值范围、碰撞与排序契约；优先明确可证明的编码范围或另存稳定决胜键。

### Q4：过期与内存淘汰为什么是两套机制？

**参考回答：**过期表达数据到何时不应继续作为有效键使用，Redis 通过访问检查和主动处理删除过期数据；淘汰是在达到内存限制时选择牺牲哪些键。未到期的缓存也可能被淘汰，没有 TTL 的键也可能在相应策略下被选中。LRU、LFU 是近似策略和实现取舍，不能承诺精确维护全局访问顺序。noeviction 也不代表没有压力，而是相应写入可能报错。为锁、幂等记录和业务状态选择策略时要考虑丢失后果，不能与可重建缓存混用而不隔离。监控同时看过期、淘汰、写入错误和回源负载。

**深入追问与答案要点：**TTL 到期事件能承担准时关单吗？不保证及时触发或可靠送达；权威定时状态、持久化任务与周期补扫才是可靠恢复的基础。

### Q5：RDB、AOF 与复制分别应对哪些丢失场景？

**参考回答：**RDB 保存某时点的数据快照，恢复装载相对直接，但快照之间的更新可能不在其中；AOF 记录写入并通过相应刷盘策略控制持久化窗口，重写用于整理恢复所需内容。复制把数据传播到其他节点，提高可用性，却可能把误删同时传播。三者目标不同，不能把一份副本当作完整历史备份。评估要区分进程退出、主机掉电、磁盘永久损坏和地域故障，测出实际可恢复的数据及时间。AOF 每秒刷盘描述策略和预期窗口，不是对任何操作系统、设备故障和调度条件的绝对一秒丢失证明。

**深入追问与答案要点：**同时启用 RDB 和 AOF 是否无需演练？仍要验证启动恢复所选路径、文件完整性、装载速度以及恢复后的冷缓存流量冲击。

### Q6：fork 与 Copy-on-Write 为什么可能导致延迟或 OOM？

**参考回答：**后台快照或重写常通过子进程处理，但创建进程时仍涉及页表等内核工作，主进程也可能短暂停顿。父子起初共享物理页，后续父进程修改共享页会触发写时复制，因此高写入率和大数据集可能让峰值内存明显增加。后台工作还有磁盘竞争和文件整理成本，“后台”不等于对主请求没有影响。容量要预留实际写入分布下的峰值内存，观察 fork 时间、写时复制量、持久化耗时和宿主压力。应在代表性数据量、写入率与容器限制下验证，避免只按常态 used_memory 配容器上限。

**深入追问与答案要点：**fork 后内存一定立刻翻倍吗？不是，初始主要共享，实际复制量取决于写入页和持续时间等；但也不能用“不立刻翻倍”推导无需余量。

### Q7：Redis“单线程”为什么不能解释所有性能问题？

**参考回答：**常见命令执行路径由事件循环串行处理，这是解释命令不互相插入的重要背景，但网络、持久化和部分释放工作可能由其他线程或进程完成，版本与配置有差别。整体延迟还包括客户端池等待、网络传输、排队、序列化和持久化影响。一个执行很久的脚本或返回超大集合会拖住其他请求，即使单个简单 GET 很快。排查应同时查看慢命令、请求大小、网络带宽和资源暂停，区分服务器执行慢与客户端等待。把线程数或分片数调大之前，先确定热点能否拆分以及下游是否有容量。

**深入追问与答案要点：**SCAN 就完全不会阻塞吗？它分批减少单次工作，但 COUNT 是提示，返回量和内部结构影响实际成本，完整扫描也不是一致快照。

### Q8：Pipeline、MULTI、WATCH 和 Lua 各适合什么？

**参考回答：**Pipeline 合并网络往返，主要提高批量吞吐，不保证整批命令作为一个业务原子动作。MULTI 与 EXEC 让排队命令在执行期间不被其他客户端命令插入，但运行时某条命令失败不会自动回滚已成功命令。WATCH 在执行前检测被关注键的变化，用于乐观重试。Lua 把读、判断和写放到服务端原子执行，适合短小的条件更新，但同样要预先验证输入和控制执行时间，不能当作自动回滚的关系事务。涉及外部数据库或跨槽键时还要重新界定边界，网络优化不能替代业务一致性协议。

**深入追问与答案要点：**先 SETNX 再 EXPIRE 是否等价于 SET NX PX？不等价；两命令之间崩溃会留下没有过期的锁。组合命令解决取得租约的原子性，仍不解决旧持有者写资源。

### Q9：Redis Cluster 的槽位与 hash tag 如何影响设计？

**参考回答：**Cluster 用固定数量的槽位分配键，客户端根据键计算槽再路由，增加节点通过迁移槽改变数据归属。槽是迁移和路由单元，不是每个节点平均分担任意单键；单热点键仍落在一个槽。多键原子操作常要求键在同槽，hash tag 可以让相关键共享哈希输入，但把整个租户所有键放同一 tag 也可能制造超级热点。设计应选择必要的共同原子边界，避免为了方便而把所有数据捆到一个槽。扩容还需验证客户端重定向、迁移失败恢复和重试语义，不能只计算总内存增加了多少。

**深入追问与答案要点：**跨槽 Lua 为什么不能靠脚本原子性解决？脚本的执行原子边界不自动跨越独立节点；应调整数据归属或改用跨系统协议，而不是假定脚本会分布式提交。

### Q10：MOVED 与 ASK 的客户端处理有什么区别？

**参考回答：**MOVED 通常告知该槽应由另一个节点处理，客户端应按返回地址重试并更新相应路由认识。ASK 用于迁移中的临时转向，客户端针对这次操作向目标节点发送 ASKING 再执行原命令，不应据此永久改写整个槽的归属。迁移时同槽的不同键可能处于不同节点，因此不能把两类响应都当普通网络错误无限重试。客户端还要限制跳转次数、总时间并正确处理连接上的临时状态。对于非幂等写，网络结果未知仍要考虑业务重试身份；重定向协议本身并没有替业务消除所有重复效果。

**深入追问与答案要点：**收到 ASK 后把本地槽表永久改到目标会怎样？可能让尚未迁移的键持续走错路径；迁移完成后的稳定归属应依据正式重定向或拓扑刷新。

### Q11：主从复制、WAIT 与故障切换能提供多强的确认？

**参考回答：**Redis 常见复制是异步的，主节点回复后副本可能尚未收到这次更新；主故障且落后副本提升，就可能失去已向客户端确认的数据。WAIT 可以等待一定副本确认复制进度，改善写入传播范围，但不能把所有持久化、选主和网络故障场景自动变成强一致事务。副本确认到内存与设备永久保存也不是同一承诺。对缓存，这主要影响可重建性与回源；对锁和余额，则可能直接破坏正确性。因此应明确故障模型、持久化和选主条件，关键不变量交由具有相应约束的权威资源维护。

**深入追问与答案要点：**主从切换后 fencing 序号回退有什么后果？旧序号可能被重新签发或错误比较，破坏栅栏前提；序号服务自身的一致性不能省略。

### Q12：布隆过滤器怎样使用才不会误伤合法数据？

**参考回答：**标准布隆过滤器用多个映射在位数组标记成员，查询有未置位位置时可以判定未加入过，全置位只表示可能存在。假阳性换取较小空间，实际概率受容量、位数和哈希数量影响。前提是所有有效成员都已经加入且没有错误删除或丢失；如果数据库新数据先可见、过滤器更新滞后，系统层面就会把合法请求误判为不存在。上线需要初始构建、增量同步、版本切换和旁路修复。它适合降低不存在请求回源，不能承担授权判断或资金唯一性，标准形式也不能随意清掉共享位来删除某个成员。

**深入追问与答案要点：**为什么“布隆没有假阴性”还会查不到新商品？数学结论以已正确加入的集合为前提；异步更新、重建切换或存储丢失破坏了工程前提。

## L2—L4 · 消息协议与选型：12 个深入问题

### Q13：Kafka 为什么能回放，消费后消息为什么不立即删除？

**参考回答：**Kafka 将记录追加到分区日志，消费者位置与记录保存策略分开，因此不同消费组可以独立推进，也能在记录仍保留时重新读取旧位置。保存受时间、大小、压缩和运维策略影响，不能承诺永久可回放。分区提供局部顺序与并行单元，事件键稳定映射有助于同业务聚合有序，但扩分区可能改变映射，生产与消费并发也会影响生效顺序。回放不只是改 offset：需要评估旧 schema、权限、去重窗口和外部副作用，避免把多年通知再次发给用户。设计前先区分审计历史与可处理事件的保留需求。

**深入追问与答案要点：**保留三天，但消费者停了五天会怎样？所需记录可能已清理；需要业务源重建或备份恢复机制，不能仅反复调整位点。

### Q14：LEO、HW、LSO 分别约束哪条边界？

**参考回答：**LEO 描述副本日志的末端位置，通常用下一条可追加的 offset 表示；不同副本的末端可能不同。HW 表示复制提交的可见边界，不能把 leader 本地追加成功直接等同所有消费者可读。启用事务且按 read_committed 读取时，还受稳定偏移边界 LSO 约束，未决事务可能让后面的记录暂时不可见，已中止事务记录也不会作为正常业务结果交付。这些位置都不是应用数据库已经处理完成的位置。排查延迟要区分生产追加、复制推进、事务完成和消费处理，单看 consumer lag 可能混淆不同阶段。

**深入追问与答案要点：**有一个长时间未提交事务会怎样？read_committed 的可见进度可能受最早未决事务限制；还应观察事务超时和处理逻辑，不能只增加消费者。

### Q15：acks=all 与 min.insync.replicas 怎样一起影响写入？

**参考回答：**副本因子说明配置了多少份副本，ISR 表示当前满足同步条件的副本集合，acks=all 按当前同步副本确认语义等待，不是固定等待配置中的所有副本。min.insync.replicas 配合相应确认方式，限制同步副本不足时是否接受写入，防止只剩一份仍悄悄降低承诺。例如三副本、最小同步副本二，故障导致同步集合不足两份时应面对拒写与重试，而不是指望参数同时提供任意故障下的可用性。还要核对选主策略和持久化故障域；确认协议不能消除所有副本同时丢失或错误操作造成的数据损坏。

**深入追问与答案要点：**ISR 有三份、min 设二，acks=all 是否只等其中任意两份？不能这样理解；min 是最低准入要求，acks=all 仍按同步副本集合的协议推进。

### Q16：Kafka 幂等生产者能否消除所有业务重复？

**参考回答：**幂等生产者使用生产者身份、序号等协议信息识别范围内的重复发送，让网络重试不必变成日志中的重复记录。相关重试、确认和在途请求设置需满足客户端约束，不能任意改参数仍声称原保证成立。但是业务代码重新调用发送、重新创建事件身份或两个独立生产者各发一次，可能都是协议看来合法的新消息。订单唯一性应来自稳定业务请求号和数据库约束，事件幂等来自消费者作用域内的稳定事件 ID。面试应分别解释网络层重发、应用层重发和业务意图重复，不能把一个开关推广成跨系统恰好一次。

**深入追问与答案要点：**关闭幂等后又允许多条在途重试有什么风险？失败批次被重试时可能与后续批次形成顺序变化，具体取决于客户端配置和版本；需按生产者官方约束验证。

### Q17：Kafka 事务的 exactly-once 应怎样划定范围？

**参考回答：**在消费 Kafka、处理后再写 Kafka 的链路里，可将输出记录与输入位点纳入同一 Kafka 事务，并让下游按提交隔离读取，从而避免输出与位点一半成功。事务身份还用于约束生产者实例的并发和恢复。但是外部数据库更新、扣款和发邮件不会自动参与，应用算完后调用一次 HTTP 成功再崩溃，重放仍可能重复调用。此时应使用外部幂等、共同提交能力或可恢复状态机。事务时间过长会影响可见性与超时恢复，设计要同时限定批量、处理时间和资源，不应把事务当作无限持续的工作流容器。

**深入追问与答案要点：**消费者设置 read_committed 就自动获得端到端恰好一次吗？没有；生产端必须正确使用事务、位点必须与输出协调，外部副作用仍有独立边界。

### Q18：消费组重平衡为什么会带来重复和暂停？

**参考回答：**组成员加入、离开或未满足活性要求时，分区归属可能重新分配。旧消费者已经拉取但尚未完成的工作，可能与新消费者从已提交位置重读重叠，因而产生重复或短暂停顿。心跳健康也不代表应用一直及时调用 poll，长时间业务处理可能触发另外的限制。处理应控制批量和单次耗时，正确处理分区撤销与分配，并对旧异步任务取消或 fencing。协作式重平衡、静态成员和新消费组协议有不同配置及行为，不能把某个版本的默认策略当永久事实。最终业务仍须幂等并可观测归属变化。

**深入追问与答案要点：**把处理线程池开大就解决 poll 超时吗？还需位点连续完成管理、队列上限、撤销后的任务控制和下游容量；否则只是从暂停变成错提交或资源耗尽。

### Q19：并行消费如何安全提交 offset？

**参考回答：**每个分区需要区分已拉取、处理中、已成功以及已提交的进度。并行处理会乱序完成，所以应推进已成功的连续前缀，而不是提交最大已完成 offset。提交位置代表恢复后下一读取位置；如果十一还没完成却因十二完成而提交十三，重启将跳过十一。提交成功后本地处理状态也要与分区归属匹配，撤销时不能让旧任务随意推进新所有者的进度。允许重复并以数据库幂等裁决，通常比提前确认制造漏处理容易恢复。日志可能有数值空隙，实际管理依据已交付记录和客户端位置语义。

**深入追问与答案要点：**只用 Redis 标记每条处理过是否足够？标记与业务效果分离会产生新的提交窗口；本地数据库效果应与去重共同事务，外部效果需外部契约。

### Q20：日志压缩与按时间删除有什么本质区别？

**参考回答：**按保留时间或大小删除主要移除旧日志段，压缩则围绕相同 key 的更新保留恢复最新状态所需记录，适合变更日志和状态重建。压缩不是立即发生，也不意味着每个 key 在任何时刻只有一条记录；消费者必须能处理历史重复版本。删除标记的保留和消费停顿时间会影响重建是否看见删除，因而恢复契约要一起设计。压缩后的 offset 可以存在空隙，不能把 offset 差直接当精确业务消息数量。若业务需要完整审计历史，只有压缩日志可能不够，还应保留独立不可变事件或满足法规的存储。

**深入追问与答案要点：**压缩会把同一 key 的金额自动相加吗？不会，它不是业务聚合引擎；记录含义与最终状态如何构建必须由应用定义。

### Q21：重试、死信和顺序要求发生冲突时怎么处理？

**参考回答：**如果同订单第二条依赖第一条，第一条失败后移到延迟队列并继续第二条，顺序保证已经改变。方案可以暂停同业务键、按版本等待前驱，或使用允许迟到和补偿的状态机，不能仅引用原队列先进先出。重试应区分暂时故障与永久格式错误，有限次数、总期限、退避和抖动共同控制资源。死信保存稳定事件身份、失败原因与处置责任，重放前修根因、验证幂等、检查业务是否过期并限速。真正的恢复指标是关键消息年龄下降和业务收敛，而不只是队列总数突然减少。

**深入追问与答案要点：**把毒消息删除后 lag 归零算恢复吗？只代表队列进度变化；必须证明业务允许舍弃，或已有补偿/重建结果和审计依据。

### Q22：RabbitMQ 发布确认、消费确认与 prefetch 怎么共同使用？

**参考回答：**发布确认用于让生产者知道 broker 是否承担发布责任，消费确认表示消费者处理投递的结果，两者彼此独立。发布确认也不代表目标消费者已执行，路由失败还需结合 mandatory 返回等机制处理。消费端通常在业务提交后 ack，确认丢失就接受重投并幂等处理。prefetch 限制未确认的投递，有助于控制在途量，但过大可能造成消息倾斜、内存增长与故障后大规模重投。队列持久化、消息持久属性和具体队列复制能力也需组合配置；不能把经典队列、quorum queue 与 stream 当完全相同的机制。

**深入追问与答案要点：**delivery tag 可以跨 channel 确认吗？不可以按任意通道处理；其作用域与确认规则必须遵守。多线程批量确认也不能越过尚未完成的投递。

### Q23：RocketMQ 事务消息解决的到底是哪一半一致性？

**参考回答：**事务消息先记录对消费者不可见的半消息，生产者执行本地事务后决定提交或回滚消息；如果最终决定丢失或未知，broker 可回查生产者的本地事务状态。它主要协调生产端本地业务结果与消息是否可投递，并不把消费者数据库或远程支付自动纳入原子事务。回查应查询可靠记录而不是重新执行一次扣款，生产者实例变化后也要能找到原事务身份。未知状态不能无限悬挂，须理解产品的检查次数、时间与失败处置配置。消费端依然可能重投，需要自己的幂等和失败恢复，不能宣称事务消息让全部链路恰好执行一次。

**深入追问与答案要点：**本地事务成功后生产者立即宕机会丢事件吗？协议提供回查恢复路径，但前提是半消息、事务标识和本地状态可恢复，最终处理还依赖所选产品配置与故障域。

### Q24：如何在 Kafka、RabbitMQ、RocketMQ 之间做可辩护选择？

**参考回答：**先列业务需要的回放期限、顺序范围、订阅模式、路由、事务协调、延迟目标和团队运维能力，再按具体版本验证。Kafka 的分区日志和消费组适合讨论多订阅、回放与流处理；RabbitMQ 的交换机路由、工作队列确认及不同队列类型提供另一组取舍；RocketMQ 的事务消息、消息组和延时能力也要结合实际产品限制。它们都有配置和故障边界，不能用吞吐大、绝不丢、金融必选这种标签替代实验。统一用同负载与故障场景比较端到端时效、重复处理、恢复能力、成本和生态集成。

**深入追问与答案要点：**换中间件能否消除业务幂等代码？通常不能；网络结果未知、外部副作用和应用重试仍存在，产品功能减少的是某些窗口和实现工作。

### Q25：Redis Sentinel 与 Cluster 的职责有何区别？

**参考回答：**Sentinel 为非 Cluster 的主从部署提供监控、故障判定、主从切换和当前主地址发现，它不把一个数据集自动按槽分片。Cluster 同时提供键槽路由、分片与对应副本故障切换，客户端需要理解拓扑和重定向。Sentinel 的 quorum 用于达成故障判定，实际发起故障转移还需要选举授权的多数条件，不能将两者当同一个阈值。两种部署都不能仅凭自动切换消除异步复制的丢写窗口。选择要先看单实例容量、单键热点、可用性目标与客户端能力，再演练网络分区和地址更新，而不是认为节点越多一致性越强。

**深入追问与答案要点：**五个 Sentinel、quorum=2，只有两个彼此可达能完成切换吗？即便满足故障判定阈值，仍无法得到多数授权；不能把判死与执行切换混为一谈。[官方：Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

### Q26：KRaft controller 与 broker 分别维护什么？

**参考回答：**KRaft 用控制器仲裁组复制集群元数据，活动控制器协调分区、注册和选主等管理状态；broker 主要保存业务分区数据并服务生产消费。两者的日志、复制集合和故障作用域不同，不能把控制器的多数派直接当作某业务分区的 ISR。Kafka 四点一按 KRaft 架构学习，不再把外部 ZooKeeper 当作必需组件。进程可以按配置承担不同角色，但生产隔离还要考虑控制面被数据负载拖累的风险。诊断时分别检查元数据仲裁健康和业务分区状态，控制器故障不等于所有已建立数据路径立即全部停止，也不保证所有管理操作照常推进。

**深入追问与答案要点：**三控制器丢两个，broker 还活着就能无限正常运行吗？不能；元数据管理和依赖它的变更会受影响，须按实际版本检查已有读写与选主行为，不能用进程存活推导完整可用性。[官方：Kafka 4.1 KRaft](https://kafka.apache.org/41/operations/kraft/)

## 练习与参考验证

1. **缓存故障放大。**入口 50000/s、命中率 99%，正常回源 500/s；缓存全失效可放大到 50000/s。参考：先按数据库安全容量限流与隔离，再讨论预热和扩容，不能把 100 倍压力原样传递。
2. **写时复制容量。**常态数据 8GB、容器限额 10GB，重写期间观察额外复制页和宿主内存。参考：不能只凭这两个数字断言一定安全或必定翻倍；要测峰值、写入分布和持续时间。
3. **确认窗口。**对消息 E7 分别在业务事务前、事务提交后 ack 前、ack 后崩溃。参考：未提交应重做，已提交重复应由唯一约束识别，提前确认而业务未提交会漏处理。
4. **积压追平。**输入 4000/s，积压 360 万，要求 20 分钟追平。参考最低成功处理能力 `4000+3600000/1200=7000/s`，还需波动余量；分区、热点与依赖容量可能阻止扩容达到该数。
5. **迁移路由。**同槽两个键分别处于源和目标节点，手推 MOVED 与 ASK 响应的客户端行为。参考：临时重定向不改永久槽归属；多键和跨槽行为必须按集群协议核实。
6. **事务回查。**本地订单成功、提交消息决定丢失。参考：回查读取原事务持久状态并返回决定，不能重复创建订单；并验证消费者重复执行时效果仍一次。
