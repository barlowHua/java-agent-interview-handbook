# 12 · 稳定性：SLO、监控、排障与容量验证

## 目标、前置与优先级

前置：Java 并发/JVM、网络、数据库与服务调用。目标：能够把一次“系统慢了”变成有证据的故障判断、止损和复盘。P0：SLI/SLO、延迟、排障、超时与限流；P1：压测、发布、容灾；P2：混沌实验与跨地域恢复。L1—L4 是深度，不是职级。目标值来自业务协商，本文数字用于练习。

## L1 · 必会口述（P0）

SLI 是观察用户体验的指标，如有效请求中的成功比例；SLO 是时间窗内希望达到的目标；SLA 是对外约定及相应后果，不能混用。定义成功需要写清分母、排除条件和统计位置。例如订单创建 SLO 为滚动 30 天内，99.9% 合法请求在 500ms 内成功，参数错误是否排除须明示，不能遇到故障临时改口径。[官方：实施 SLO](https://sre.google/workbook/implementing-slos/)

错误预算是允许不达标的份额。若 30 天有 1000 万有效请求，99.9% 请求型 SLO 允许约 1 万次坏事件；这与“允许停机 43.2 分钟”的时间型推导不是同一分母。预算用于决定发布与可靠性投入，不能理解为可以主动制造故障。

延迟看分布而非仅均值。P99 表示 99% 样本不超过该值，不能把多台机器的 P99 简单求平均得到整体 P99。应聚合兼容直方图或原始样本后求分位数，同时记录超时和被拒绝请求，避免只统计成功请求造成幸存者偏差。

## L2 · 机制与监控（P0/P1）

入口关注请求量、错误、延迟；资源关注利用率、饱和度和错误；业务关注成功完成量、待处理年龄、重复或差异。指标发现趋势，日志解释事件，链路追踪定位关键路径，profile 解释 CPU/分配等热点。trace ID 需要贯穿异步事件，但日志不应泄露凭据或完整个人信息。[官方：监控](https://sre.google/workbook/monitoring/)

告警应优先反映用户影响并能行动。燃烧率 `当前坏事件比例/允许坏事件比例`：99.9% 目标允许 0.1%，当前 1% 错误即 10 倍燃烧。持续一小时约消耗 30 天预算的 `10/720≈1.39%`，假设流量近似均匀；请求型预算在流量剧烈变化时应按实际请求数核算。长短窗口组合有助于兼顾快速识别与持续性确认。[官方：SLO 告警](https://sre.google/workbook/alerting-on-slos/)

超时应由总 deadline 逐层分配，给网络连接、业务处理和响应留预算；下游取消要尽可能传播。限流控制进入速率，并发隔离限制在途资源，熔断在依赖持续失败时快速拒绝，降级提供明确减损功能。它们不能互相替代。队列必须有上限，过长排队会让已经超时的请求继续浪费资源。

## L3 · 排障与压测（P0）

故障处理顺序是确认用户影响与范围，保留关键证据，采取可逆止损，再验证恢复。先查近期发布、配置和流量变化，但时间相关性不是因果证明。候选原因要能产生可区分的预测，例如“连接池等待升高但数据库执行不慢”与“数据库锁等待升高”对应不同处理。

Java 接口 P99 激增时，按链路拆入口排队、线程池、连接池、下游与 GC。CPU 高可看线程采样和 profile；CPU 低但慢可查锁、I/O、依赖或排队。堆不断增长需区分正常缓存与泄漏，结合 GC 后存活量、分配率和对象引用。生产抓取 heap dump 或高频 profiling 有开销，应按影响评估与操作流程执行。

### 看图：从“慢”走到可证伪的根因假设

![Java 服务 P99 变慢的计算、等待与 GC 证据链](assets/12-diagnostic-evidence.svg)

**读图顺序：**先确认顶端用户影响与样本可比性，再按 CPU、等待和 GC 三个证据方向展开，最后用可逆操作检验假设。三条分支可以同时成立：慢依赖导致请求堆积，保留对象变多，又引发 GC；根因和放大因素不能混为一谈。

**记忆锚点：**“指标发现，trace 定位，日志解释，profile 归因，实验验证”。trace 的父子 span 可能重叠或并行，不要简单把每个子 span 的耗时相加当总耗时；也要防止只采到成功请求。数据库慢查、连接池等待与事务持有时长应分别测量。

| 观察到的证据 | 候选解释 | 下一步区分证据 |
| --- | --- | --- |
| 连接池等待高，SQL 执行正常 | 持有连接太久、连接泄漏、并发超额 | 对齐 borrow/return、事务时长、持有者栈 |
| CPU 高，固定方法占据采样 | 计算热点或忙循环 | 相同流量下对照 profile 与发布版本 |
| CPU 使用低，却有容器节流 | 配额短周期耗尽或调度影响 | 看 throttling、可运行线程及宿主压力 |
| GC 后存活量持续增长 | 有界缓存未稳定或对象被长期持有 | 对齐流量/缓存上限，查保留路径与长期趋势 |
| 锁等待和 SQL 延迟同步增加 | 长事务或热点行竞争 | 构造持锁者—等待者关系，定位最早持锁原因 |

**适用限制：**表格是生成假设的方法，不是观察到一项指标即可定罪。工具采样、时钟、trace 丢失和测量边界都会影响结果；采集开销也应计入线上操作判断。

**闭卷重画：**给出“CPU 低、连接池满、SQL 单次仅 5ms”的三种解释，各写一条能排除该解释的证据，再选一个可逆止损方案。

### deadline 与重试：把延迟预算写成数字

假设入口总预算 800ms，认证和排队已用 80ms，序列化/回传保留 70ms，则下游与退避合计只剩 650ms。若首次尝试用了 400ms、退避 100ms，只剩 150ms 可用于第二次，不能再次分配完整 650ms。连接建立、TLS、读超时、连接池等待是否计入 SDK 超时要按实现核对；外层 deadline 到期也不证明下游业务已取消。对于写操作，截止时间到达后仍要保存“结果未知”及查询身份。

燃烧率告警之外还应设置“没有流量/遥测中断”的监控，否则失败的采集系统可能让错误率看起来变低。恢复判定需观察成功吞吐、长尾、队列年龄和业务差异同时改善，不能只看告警消失。



压测先写负载模型：比例、数据分布、热点、并发/到达率、思考时间、请求体与运行时长。闭环固定并发会在系统变慢时减少新请求，可能掩盖真实峰值压力；开放到达率模型更适合检验外部持续流量，但也要验证压测端没有先触顶。测容量阶梯、突发、长稳态和单依赖故障，记录拐点与恢复时间。压测结论必须附版本、环境、样本量和瓶颈，不能把测试机 QPS 直接等同生产容量。

## L4 · 拓展边界（P2）

RPO 是允许丢失的数据范围，RTO 是恢复服务的时间目标；必须通过恢复演练验证。多副本不能替代备份，备份成功不等于恢复成功。发布用灰度、版本兼容和自动停止条件，数据库 schema 采用先兼容扩展、迁移，再收缩的步骤。混沌实验先定义稳态、影响半径、终止条件和恢复动作，不能把随机破坏当成稳定性能力。

## 六道核心题：60～90 秒参考回答与追问

### 1. 如何为一个服务制定 SLO？

**参考回答：**先识别关键用户旅程，定义可测的好事件，例如合法订单请求在约定时间内成功，明确分母、排除条件和测量位置。根据业务需求和当前能力协商目标与时间窗，再建立错误预算和告警。异步业务还要衡量任务完成时效，不能只看受理接口。目标过高会浪费成本，过低会损害体验，因此要有真实流量基线、负责人和预算耗尽时的行动规则。每次调整口径都记录原因，避免通过排除失败美化指标。例如订单接口返回已受理，但后台任务两小时后才处理，这对同步接口可用率可能没有影响，却已经伤害用户体验。因此需要另定义受理到完成的时效分布，并把长期待处理任务计入不达标事件，不能只监控前台成功响应。

**追问：99.99% 一定优于 99.9% 吗？**体验目标更高，但额外成本是否值得取决于业务损失、依赖上限和实现成本。

### 2. CPU 不高，但接口很慢，如何排查？

**参考回答：**CPU 低只说明计算可能不是当前瓶颈。我先拆时间花在入口排队、线程池、连接池、网络、锁还是数据库。结合 trace、线程栈和池指标，找最长等待和它依赖的资源，再看近期变化及影响范围。例如连接池等待高但 SQL 执行快，可能是连接未释放或事务持有过久；下游响应慢则要收紧超时与隔离。先采取可逆措施控制用户影响，再用证据验证原因，避免盲目增加线程把压力传给下游。例如线程栈显示大量请求等待同一个远程连接，增加应用机器可能只是增加争抢。应确认目标依赖是否达到配额或连接数上限，再控制入口并发与超时；若近期发布改变了请求次数，用灰度回滚检验这个假设是否成立。

**追问：线程数增加为什么更慢？**会放大上下文切换、连接竞争和下游并发，排队只是从一个地方转移到另一个地方。

### 3. 如何防止重试风暴？

**参考回答：**明确唯一主导重试层，限制单请求尝试次数和总截止时间，对暂时性错误指数退避加抖动，对无效参数等永久错误不重试。有副作用的操作先保证幂等。服务端用并发上限、队列上限和限流保护资源，依赖持续失败时熔断，恢复时逐渐放量。指标同时统计原始请求和所有尝试，才能看到放大倍数。测试要模拟依赖变慢和失败，观察重试是否推高负载而延长恢复。例如依赖正常能处理一千次请求，故障时每个上游都额外尝试三次，恢复初期可能仍被重试淹没。我会为重试设置独立预算或令牌，并优先保障新请求和重要业务，让恢复容量能够消化积压而不是再次耗尽。

**追问：指数退避为什么还需要抖动？**大量客户端同刻失败时可能在相同时间再次重试；抖动分散同步波峰。[官方：重试控制](https://docs.aws.amazon.com/wellarchitected/2024-06-27/framework/rel_mitigate_interaction_failure_limit_retries.html)

### 4. 如何判断压测报告可信？

**参考回答：**我看目标、环境和负载是否代表生产：数据量与热点、读写比例、请求大小、缓存冷暖、依赖延迟和到达率都影响结果。报告需要同时给吞吐、错误率、P95/P99、资源饱和与测试持续时间，检查压测机没有成为瓶颈。单次短峰值不证明稳定容量，还要测长时间运行、失去一个节点和故障恢复。最终给出满足 SLO 的安全容量及限制条件，而不是只展示错误很多时的最高 QPS。例如在全热缓存、小数据集上得到的高吞吐，无法证明大数据扫描、热点更新和冷启动时表现相同。报告应说明覆盖和未覆盖的场景，给出首先触顶的资源；扩容结论还需要验证增加实例后共享数据库没有成为瓶颈。

**追问：为什么闭环压测可能低估问题？**响应变慢后请求发出速度也下降，真实外部流量不会一定跟着下降，排队压力可能被隐藏。

### 5. 一次线上事故应如何复盘？

**参考回答：**按事实整理时间线、影响用户与业务损失，区分触发条件、根因、放大因素和检测恢复缺口。用证据解释为什么原有保护没生效，而不是止于某人操作失误。改进项要有负责人、截止时间和验收标准，例如补幂等约束、缩短发现时间、演练恢复；不只写加强监控和注意操作。还要检验同类系统是否存在相同风险，并验证行动完成后的效果。复盘的价值是降低复发概率和缩短恢复，而非寻找替罪者。例如触发因素是一次配置变更，放大因素可能是无限重试，发现慢是缺少用户侧告警，恢复慢是回滚脚本不可用。把这几个层次分开，才能形成具体改进；不能只要求下次发布仔细检查而保留相同系统脆弱点。

**追问：回滚成功就不用找根因吗？**回滚只是止损证据，仍需查明机制，否则下次发布或流量变化可能再次触发。

### 6. 如何验证容灾方案？

**参考回答：**先定义故障域以及 RPO/RTO，再检查应用、数据库、消息、身份、配置和 DNS 是否共享单点。演练包含数据恢复、流量切换、容量验证和回切，记录实际丢失范围与恢复时间。还要测试切换过程中的重试、重复写入和旧主恢复，避免双写破坏状态。备份应定期抽样恢复并校验业务一致性。仅在图上有两个机房或多个副本，不能说明能承受整区故障。例如主库所在区域不可用后，备区数据可能落后，切换不能只看实例健康；要根据恢复点目标决定能否开放写入。故障区回归也不能直接同时接流量，应先处理旧主身份、数据分歧和回切验证，避免把单次故障变成双写事故。

**追问：RTO 只包含机器启动时间吗？**不包含这么窄；还要覆盖检测、决策、数据恢复、切流和达到可用业务状态的全过程。

## 易错点

- 平均延迟正常不能证明用户体验正常。
- HTTP 200 不一定代表业务完成；拒绝和超时不能悄悄从指标消失。
- 扩容不能解决所有锁竞争或外部配额问题。
- 故障期间先止损，但关键证据应在成本允许时及时保留。

## 练习、参考思路与验证

为订单 API 定义一个请求型 SLO 和一个履约时效 SLO，计算 1000 万请求下 99.9% 的预算。构造 5 分钟错误率 5%、一小时 1% 的情形，说明如何用长短窗口判定持续燃烧；参考结论：短窗捕获当前影响，长窗防止孤立噪声，阈值需与业务预算消耗目标对应。再写“数据库变慢”演练：逐步注入延迟，观察线程/连接/队列是否有界、取消是否传播、恢复后积压是否收敛。

## 过关标准

六题闭卷回答；能以一张图解释用户影响到资源原因的证据链；能给出含错误率与尾延迟的容量结论；能用具体数据计算预算与净积压恢复时间，并完整讲述一次真实或可复现实验事故。
