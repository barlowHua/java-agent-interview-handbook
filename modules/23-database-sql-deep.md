## L1—L2 · SQL 与索引：12 个深入问题

### Q1：SQL 的逻辑执行顺序和数据库实际执行顺序有什么区别？

**参考回答：**逻辑顺序帮助确定结果语义：先形成来源和连接关系，再过滤行、分组聚合、过滤分组、计算选择结果与窗口、排序并取有限行。它不表示数据库一定按这个次序逐行执行。优化器可以下推谓词、调整连接顺序或选择索引，只要维持语义约束。外连接、聚合和窗口会限制可做的改写。例如把右表条件从左连接的 ON 移到 WHERE，可能删掉补 NULL 的行，改变结果。我会先用小数据证明结果，再用实际参数的执行计划验证代价，不从 SQL 的书写顺序推断运行算法。

**深入追问与答案要点：**为什么窗口函数的结果一般不能直接在同层 WHERE 中过滤？窗口计算作用于已通过过滤的行集；使用派生表或 CTE 计算后再过滤，见实验 4。逻辑顺序是理解工具，不是承诺具体物理算子顺序。

### Q2：LEFT JOIN 的 ON 条件与 WHERE 条件怎样改变结果？

**参考回答：**左连接会为找不到匹配右行的左行补 NULL。放在 ON 中的右侧条件参与匹配判断，不会因此删掉该左行；放在 WHERE 中的条件则过滤连接后的结果，普通相等比较对补出的 NULL 得到未知，会把它排除。这就是查全部客户及已付订单时，条件放错位置导致零订单客户消失的原因。还要注意一对多连接会放大行数，后续直接求订单金额可能重复累计。我会明确期待的结果粒度，必要时先在右侧聚合或用 EXISTS 判断存在，而不是加 DISTINCT 掩盖重复。

**深入追问与答案要点：**加上 `WHERE o.status='PAID' OR o.id IS NULL` 总等价吗？不总是；如果客户只有不符合状态的真实匹配行，连接不会生成补空行，WHERE 仍会把它删掉。把过滤放入 ON 才保留这种客户。

### Q3：NULL、COUNT 与 NOT IN 为什么经常产生意外结果？

**参考回答：**NULL 表示未知或缺失，普通等号比较不会把两个 NULL 当作相等，需要用 IS NULL 等专门语义。COUNT 星号统计行，COUNT 列只统计非空值，SUM 和 AVG 通常忽略空值，但空集合的结果也要区分。NOT IN 的子查询若包含 NULL，原本不在列表中的值也可能得到未知而被 WHERE 排除，因此反连接常用相关 NOT EXISTS，并明确两边可空列的业务含义。不要通过全局把 NULL 改成零来修复，因为未知金额、真实零金额和缺少订单是三种不同事实。测试也应包含空表与空金额两类样本。

**深入追问与答案要点：**外连接后 `COUNT(*)` 能表示订单数量吗？不能，补空的左行也计入；使用右表非空主键的 `COUNT(o.id)`，并注意连接膨胀。

### Q4：GROUP BY、HAVING 和窗口函数分别保留什么粒度？

**参考回答：**分组聚合把同组多行折叠成一行，HAVING 在组级结果上过滤；窗口函数在选定分区和排序内计算，但通常保留每条输入行。统计每位客户总额用分组，给每笔订单附客户累计额或名次用窗口。窗口的分区、排序和 frame 是三个维度，默认 frame 在存在同排序值时可能把并列行一起纳入，不能把它永远当逐行累加。需要按行累计就显式定义 ROWS 边界和稳定排序键。开启严格分组语义时，不能随意选择既未聚合也不由分组键决定的列。

**深入追问与答案要点：**同分第一名需要保留几条？取决于业务。ROW_NUMBER 强制编号，RANK 保留并列并跳号，DENSE_RANK 保留并列而不跳号；不能只靠一个函数名回答“每组前二”。

### Q5：每组 Top N 为什么要明确并列和确定性？

**参考回答：**每组 Top N 有两种不同需求：严格返回 N 条，或返回前 N 个名次的全部并列记录。前者可按业务分数与唯一 ID 排序后用 ROW_NUMBER，后者按分数使用 RANK 或 DENSE_RANK，再解释是否跳号。排序只写创建时间而时间相同，数据库可以用任意合法顺序排列，并发翻页时更容易出现重复或遗漏。窗口排序也不自动保证最终输出顺序，最外层仍要 ORDER BY。我会把同分、空值、少于 N 条和重复时间都放进测试数据，让结果契约在实现前固定。

**深入追问与答案要点：**在排名表达式里加入 ID 会怎样？唯一 ID 可能打破原本需要保留的并列；可以一个窗口按分数计算并列排名，另一个窗口按分数加 ID 计算确定性行号。

### Q6：OFFSET 深分页与游标分页分别有哪些成本和语义？

**参考回答：**大 OFFSET 常需要找到并跳过大量前序候选行，后面只返回二十条不代表前面没有代价。游标分页用上一页的稳定排序键作为下一页范围起点，配合匹配索引可以缩小访问范围，但失去任意跳页便利。排序应包含唯一决胜字段，例如创建时间和 ID，方向及条件必须一致。并发新增、删除或排序字段更新仍会影响可见性；游标不是自动快照。如果产品需要一致导出，要采用明确的快照或冻结边界，而不是长期占住在线业务事务而不评估版本保留成本。

**深入追问与答案要点：**降序 `(created_at,id)` 下一页怎样写？使用时间更小，或时间相同且 ID 更小的条件；看实验 5。若存在 NULL 排序键，必须另外定义空值的位置和游标编码。

### Q7：联合索引怎样同时服务过滤、范围与排序？

**参考回答：**联合索引按列逐级排序。等值条件固定前导列之后，后续列的区间和顺序更容易映射为连续范围，因此租户、状态、时间、ID 可以服务特定列表查询。但字段顺序应来自实际查询组合和数据分布，不能机械采用选择性最高优先。一个范围条件可能限制后续列继续缩小搜索区间，却不表示后续列完全无用；它仍可能用于索引内过滤或覆盖。排序方向、函数表达式和类型转换也会影响计划。我会同时比较扫描量、返回量、回表、排序与写放大，而不是只报告命中某个索引。

**深入追问与答案要点：**给四列分别建索引能替代四列联合索引吗？通常不能提供相同的有序复合访问路径；优化器可能做索引合并，但是否有收益须看具体计划。

### Q8：覆盖索引、ICP 与索引合并到底减少哪部分工作？

**参考回答：**覆盖索引让查询所需列能从索引得到，主要减少为了取列而访问聚簇行的需要。ICP 把能只靠索引列判断的条件交给存储引擎，在读取完整行之前排除候选，减少回表数量；它不自动缩小所有索引扫描区间。索引合并则把多个索引访问得到的行身份做合并或交集，涉及额外成本，不能等同一个匹配排序的联合索引。三者可以解决不同瓶颈，面试应举同一查询比较访问行数与返回列。对于覆盖也保留 MVCC 例外，不能承诺物理上任何时候都零回表。

**深入追问与答案要点：**`Using index` 和 `Using index condition` 是一回事吗？不是。前者常指索引覆盖访问，后者指条件下推；输出格式、算子和是否回查要结合完整计划与当前版本解释。

### Q9：为什么优化器会放弃你认为更好的索引？

**参考回答：**优化器选择估计成本较低的计划，估计依赖统计信息、基数、数据分布与访问代价。某状态在总体稀少但某个租户极常见，组合相关性可能让估计偏差；统计陈旧、参数差异和返回大范围记录也会改变选择。全表顺序扫描有时确实比大量随机回表便宜，所以“不选索引”本身不是错误。排查时先固定实际参数和环境，比较估计与实际行数，查数据倾斜，再评估更新统计、索引重排或查询重写。强制索引可能暂时奏效，但会固化对当前分布的假设并造成后续回归。

**深入追问与答案要点：**直方图解决所有组合列相关性吗？不能；它能改善部分分布估计，但不自动表达任意跨列关系。最终仍要在代表性参数和数据上验证。

### Q10：EXPLAIN ANALYZE 中哪些数字最值得追？

**参考回答：**我会先找估计行数与实际输出差异最大的算子，再看它执行的循环次数以及下游是否放大工作量。一次索引查找很快，若嵌套执行几十万次，总成本仍然巨大；同样输出二十行，可能已经扫描百万行。执行时间不能不加分析就把父子算子全部求和，需遵循计划展示语义。还要结合锁等待、池等待和网络，防止把端到端延迟全归 SQL。ANALYZE 会真正执行受支持语句，所以先用脱敏参数在受控环境评估，再决定生产采样范围，保留优化前后可对比证据。

**深入追问与答案要点：**只看到 filesort 能断言落盘吗？不能；名字不意味着必然磁盘排序。需要看排序规模、内存及运行统计，且排序本身可能是最经济的选择。

### Q11：Nested Loop 与 Hash Join 应该怎样解释取舍？

**参考回答：**嵌套循环把外侧行带入内侧匹配，若内侧有高效索引且外侧结果小，访问很经济；若外侧巨大而每次内侧扫描多行，成本会迅速放大。哈希连接通常为一侧建立按连接键检索的结构，再用另一侧探测，适合相应的等值连接场景，但需要内存且可能发生分区和磁盘工作。不能把哈希连接当作所有版本、所有连接条件的固定默认。优化关键是连接顺序、输入过滤、行宽与基数，不只是更换算法。我会用同一数据集的计划确认实际算子，再验证缓存冷暖和倾斜对结果的影响。

**深入追问与答案要点：**“小表驱动大表”永远正确吗？不应只看表总行数；应看过滤后的输入、内侧访问路径、连接算法和输出规模，外连接等语义还限制重排。

### Q12：加索引和在线 DDL 为什么也会导致线上故障？

**参考回答：**索引建设会扫描和排序数据、消耗 CPU、磁盘和临时空间，还会增加后续写入维护成本。所谓在线通常表示允许某种并发访问，并不代表完全没有元数据锁或切换阶段等待。一个长事务持有元数据锁时，DDL 可能等待，后续请求又排在它后面，形成看似突然的全站阻塞。上线前要核对目标版本、具体变更所支持的算法和锁模式，估算空间、观察长事务并设置中止条件。变更后验证计划和写入尾延迟，删除索引也要确认其他业务路径没有依赖，不能只优化一个查询。

**深入追问与答案要点：**INSTANT、INPLACE、COPY 是固定表能力吗？它们取决于具体操作、引擎、版本和表特征；应查操作矩阵并明确不支持时是否拒绝或回退。

## L2—L4 · 事务、日志与演进：12 个深入问题

### Q13：Read View 的可见性为什么不能只比较事务 ID？

**参考回答：**事务 ID 大小主要反映分配顺序，不直接等同提交顺序。一个更早开始的事务可能仍未提交，另一个更晚事务已经提交，所以读视图要保留创建时的活跃集合和边界。读取当前版本不可见时，通过 undo 重建更早版本直到可见或确认没有可见行。自身修改具有特殊可见规则，因此同一事务可能看见自己更新的行与其他行旧版本组合。RR 通常复用首次一致性读视图，RC 每次建立新视图。解释时要同时给出事务何时开始、何时建立视图、何时提交，省略任何一个都可能得出错误结论。

**深入追问与答案要点：**一个最早开始的事务是否一定能看到后来事务的提交？不一定；关键是具体读的视图何时创建或更新，而不是 BEGIN 的时间。

### Q14：记录锁、间隙锁与 next-key lock 怎么按 SQL 推断？

**参考回答：**记录锁保护索引记录，间隙锁限制相应间隔插入，next-key 将记录与前方间隙组合。推断锁范围先确定隔离级别、实际访问索引、条件是否唯一等值以及目标是否存在，不能只看 WHERE 字面范围。唯一索引命中已有行时通常无需锁前方间隙；非唯一范围扫描会涉及不同保护范围。缺少适合索引可能锁住远超业务意图的记录。间隙锁的作用主要是抑制插入，不能按普通互斥记录锁完全类比。我会用两连接控制提交时序，再通过锁等待表验证，而不是只画理论区间。

**深入追问与答案要点：**RC 是否完全没有间隙锁？不是；一般减少用于搜索/扫描的间隙锁，但外键和重复键检查等仍有例外。具体锁边界以当前语句与版本为准。

### Q15：RR 为什么仍不能自动维护跨行的业务约束？

**参考回答：**隔离级别规定读写可观察行为，并不理解“至少一位医生值班”这种业务不变量。两个事务分别读取同一份满足约束的快照，然后更新不同医生行，彼此没有相同记录上的写冲突，可能都认为退出安全。只保证每行修改原子并不足以约束组合结果。可以把不变量收敛到一条共同资源记录，用条件更新或按统一顺序锁定相关记录，再选择合适隔离与重试策略。关键是把业务判断和修改放在能被并发裁决的边界；一概升级隔离也要评估范围锁、死锁和吞吐，不能省略实验。

**深入追问与答案要点：**乐观版本号放在每个医生行就够了吗？不一定；两事务各改不同版本行仍不冲突。需要覆盖共同约束的版本或共同锁定对象。

### Q16：死锁、锁等待超时与提交结果未知该如何分别处理？

**参考回答：**死锁是等待图成环，数据库会选择牺牲事务；锁等待超时可能只是长时间排队，未必成环。不同错误的回滚范围并不相同，例如 InnoDB 锁等待超时通常回滚当前语句，配置可以改变行为，不能假定剩余事务状态已清理。提交时连接断开又是另一类：客户端不知道事务是否成功，需要依靠稳定请求身份查询结果。应用应明确异常分类、回滚连接和有界重试，重复执行业务前确认没有不可重复的外部副作用。死锁修复还要检查访问顺序与扫描锁范围，只增加超时时间往往会扩大拥塞。

**深入追问与答案要点：**死锁后只重试最后一条 SQL 可以吗？通常应重试完整逻辑事务，并重新读取依赖状态；具体驱动和事务框架如何标记回滚必须核实。

### Q17：redo、undo、binlog 与脏页刷盘怎样分工？

**参考回答：**数据页通常先在内存修改，提交不必同步写完所有脏页。redo 记录支持崩溃恢复所需的修改信息，WAL 要求对应日志按规则先于脏页持久化；undo 支持撤销和历史版本重建，binlog 记录服务层复制和恢复需要的变更。它们面对不同恢复目标，因此互相不能代替。日志也并非无限增长：redo 空间复用依赖检查点推进，长事务会影响 undo 清理。排查写入抖动要结合日志刷盘、检查点、脏页比例和设备延迟，不能把每次变慢都叫锁问题。配置选择最终由可接受丢失量与恢复时间约束。

**深入追问与答案要点：**redo 是 SQL 重放吗？不能如此概括；它服务存储引擎的数据恢复，与服务层 binlog 的记录形式和使用方式不同。也不要把 undo 简化成每条语句的一条反向 SQL。

### Q18：MySQL 内部两阶段提交与业务 2PC 有什么不同？

**参考回答：**开启相应日志机制时，MySQL 需要协调存储引擎提交状态和 binlog 中的事务记录，避免恢复后出现引擎与复制日志认定不一致。可以用准备、记录提交依据、完成引擎提交理解这个协调，但真实执行还有组提交和持久化步骤，不能把三行教学伪代码当完整磁盘时序。崩溃恢复依据持久化的准备状态和提交证据决定继续提交或回滚，正确性也受刷盘策略与故障模型限制。这是数据库内部协调，不意味着一个应用事务已经覆盖远程支付、其他数据库或消息服务。业务跨系统仍要明确参与协议与恢复负责人。

**深入追问与答案要点：**只把 `sync_binlog=1` 打开是否足够？还要结合引擎日志策略、设备持久化保证、复制与故障域；某个参数不能单独提供全部数据安全。

### Q19：长事务为什么会同时影响空间、锁和查询？

**参考回答：**事务长期保持未结束状态，会延长它持有的锁与资源生命周期；若还保有需要旧版本的读视图，相关 undo 不能立即回收，历史链和磁盘压力可能增加。长时间一致性导出虽然减少读锁冲突，也并非免费。更隐蔽的情况是业务拿到连接后调用远程服务，数据库本身没执行慢 SQL，却一直占用连接和锁。排查需把事务开始、连接借还、最近语句与等待者关联，不能只查当前正在跑的 SQL。修复通常是缩小事务边界、批量分段并定义快照语义，对大导出另选隔离资源与恢复方案。

**深入追问与答案要点：**没有加行锁的只读事务就没有影响吗？不成立；旧快照可影响历史版本清理，持有连接与元数据相关资源也有代价。

### Q20：异步复制、半同步与“读到刚写的数据”是什么关系？

**参考回答：**异步复制允许主库完成后副本尚未接收或应用，因此读副本可能落后。半同步在约定时点等待至少满足条件的副本确认，但确认接收持久化复制日志并不等同 SQL 已应用、任意副本都可读到新数据。超时降级策略与提升哪个副本也会影响丢失风险。读己之写可选择短期路由主库，或携带复制进度并等待指定副本达到要求；等待必须有超时与降级。用固定睡眠赌复制完成只是在当前延迟分布下碰运气。设计时分别约定写成功含义、复制确认、可读状态和故障切换后的恢复点。

**深入追问与答案要点：**副本延迟字段为零是否证明所有客户端都能读最新？不能；需理解测量点、复制通道、事务应用与读路由，单个观测字段不足以证明完整语义。

### Q21：主库故障切换最危险的地方是什么？

**参考回答：**危险不只是新主多久启动，而是旧主是否还能接受写入、候选副本是否包含必须保留的事务、客户端是否真的切到新主。没有隔离旧写入权限就提升新主，可能形成双主分歧；只根据机器健康而忽视复制进度也可能丢失已承诺业务。流程要包括故障判定、旧主 fencing、候选选择、数据检查、路由切换、容量验证和恢复后的回切。业务请求可能在切换边界结果未知，因此仍需幂等与对账。RPO 和 RTO 应通过演练得到，复制拓扑图与自动选主开关并不是恢复能力的证明。

**深入追问与答案要点：**旧主恢复后能直接挂回去吗？先确认权威角色和数据是否分歧，再按产品流程重建或追平；不能让恢复的旧主自动继续独立写。

### Q22：分片键如何从业务访问模式选择？

**参考回答：**分片键决定一次核心请求能否在单片完成，也决定热点和后续扩容方式。按用户分片适合用户订单列表，却使商家跨用户报表困难；按租户可保持租户内事务，但超级租户可能压满单片。不能只看均匀哈希和当前数据量，还要估计单键写入、范围查询、全局唯一性以及跨片操作比例。对非主访问模式可以建设异步搜索或分析视图，并明确延迟。路由规则应集中并带版本，预留迁移与大租户独立路由。只有证明单库优化、归档和读扩展仍不满足要求后，分片复杂度才值得承担。

**深入追问与答案要点：**分片后全局唯一约束放哪里？选择具有可证明唯一性的 ID/业务归属，或设计专门唯一性服务；各片自己的唯一索引只能约束片内。

### Q23：在线迁移如何避免双写把问题变得更复杂？

**参考回答：**迁移先定义新旧系统的权威关系和切换条件，再做基线复制、增量追平、校验、小流量切换与回退。简单同时写两个库会出现一个成功一个失败，并不能自动成为一致方案；需要可恢复的变更日志、幂等应用、版本顺序和对账。校验既看行数与校验和，也看金额、状态和业务关联，避免字段映射错误被掩盖。切换期间旧请求和后台任务可能仍写旧库，应有路由版本或写入 fencing。回退前确认新侧增量是否能返回旧侧；只切 DNS 而丢掉切换后的合法写入不算有效回滚。

**深入追问与答案要点：**“双读结果相同”就能直接切写吗？还要验证写约束、触发器、默认值、并发语义、迁移滞后与故障恢复；读样本一致只覆盖部分证据。

### Q24：备份和 binlog 恢复怎样证明能满足业务？

**参考回答：**首先确认基线备份可用、日志连续且恢复目标时点可定位，再在隔离环境完成真实恢复。验证不只看数据库能启动，还要检查业务数量、金额、关联约束、账户权限以及应用能否读取。误删恢复常需要恢复到事件之前并选择性补回，直接把线上整体倒退会丢掉之后的正常业务。记录数据丢失范围、恢复耗时和依赖准备时间，才能判断 RPO、RTO 是否满足。备份本身还需隔离故障域、控制访问和保留多个历史点，因为在线副本会复制误操作，不能替代独立备份与恢复演练。

**深入追问与答案要点：**恢复演练只选一张小表可以吗？它只能验证部分路径；还需覆盖全量大小、日志回放速度、跨表一致性和切流过程，并说明未覆盖的风险。

### Q25：连续登录日期为什么要先去重，再用窗口分组？

**参考回答：**同一天多次登录不能重复增加连续天数，因此先按用户与业务日期去重，再在每个用户内按日期递增编号。对于没有缺口的一段日期，日期减去行号天数得到相同分组键，缺一天则键改变，因此可以按该键聚合起止日期与天数。直接对原始登录流水编号会让重复日期打断或伪造连续段。还要先把时间戳转换成约定的业务时区日期，否则午夜附近的事件会分到不同日；夏令时下连续日也不等于固定二十四小时时间差。最后明确至少几天、跨月跨年和缺失日期语义，用包含重复与断点的数据验证。

**深入追问与答案要点：**日期是每隔七天连续一期怎么改？不能照抄减一天的分组键，应先定义周期编号或把日期规范化到周序号，再建立正确的连续关系。

## 九组 SQL 推演与预期结果

下面是原创小数据练习。九组查询已在本轮新建的隔离 MySQL 9.3.0 实例实跑，输出全部与预期一致；[验证记录与命令](../labs/05-sql-worked.md)说明环境、范围及关闭过程。课程的 InnoDB 机制基线仍是 8.4，这次通用 SQL 结果验证不代替 8.4 的锁、执行计划与复制实验。金额故意包含 NULL，用于说明未知值与零的区别。

```sql
CREATE TABLE drill_customer(id INT PRIMARY KEY, name VARCHAR(20) NOT NULL);
CREATE TABLE drill_order(
  id INT PRIMARY KEY, customer_id INT NOT NULL,
  amount INT NULL, status VARCHAR(12) NOT NULL, created_at DATE NOT NULL
);
INSERT INTO drill_customer VALUES (1,'甲'),(2,'乙'),(3,'丙'),(4,'丁');
INSERT INTO drill_order VALUES
 (101,1,100,'PAID','2026-10-01'),
 (102,1,100,'PAID','2026-10-01'),
 (103,2,50,'PENDING','2026-10-02'),
 (104,2,NULL,'PAID','2026-10-03'),
 (105,3,80,'PAID','2026-10-04');
```

### 推演 1：WHERE 与 HAVING

```sql
SELECT customer_id, SUM(amount) AS total
FROM drill_order WHERE status='PAID'
GROUP BY customer_id HAVING SUM(amount)>100
ORDER BY customer_id;
```

预期只有 `(1,200)`。客户 2 的已付金额只有 NULL，SUM 得 NULL，`NULL>100` 不为真；客户 3 为 80。把 WHERE 删掉会将待支付金额纳入统计，这属于口径变化，不是优化。

### 推演 2：COUNT 与 AVG

```sql
SELECT COUNT(*) AS rows_n, COUNT(amount) AS known_n,
       SUM(amount) AS total, AVG(amount) AS avg_known
FROM drill_order;
```

预期 `5,4,330,82.5`。AVG 的分母是四个非空金额，不能回答 330/5；真实财务指标若要求未知值算零，必须明确业务口径，再显式使用 COALESCE。

### 推演 3：零订单客户与外连接

```sql
SELECT c.id, COUNT(o.id) AS paid_n
FROM drill_customer c LEFT JOIN drill_order o
 ON o.customer_id=c.id AND o.status='PAID'
GROUP BY c.id ORDER BY c.id;
```

预期 `(1,2),(2,1),(3,1),(4,0)`。将状态条件移到 WHERE 后客户 4 消失；将 COUNT(o.id) 改为 COUNT(*) 后客户 4 变成 1。这是两个独立错误。

### 推演 4：每组最新一笔与并列排名

```sql
WITH ranked AS (
 SELECT id,customer_id,amount,
  ROW_NUMBER() OVER(PARTITION BY customer_id
                    ORDER BY created_at DESC,id DESC) AS rn,
  DENSE_RANK() OVER(PARTITION BY customer_id ORDER BY amount DESC) AS dr
 FROM drill_order
)
SELECT id,customer_id,amount,dr FROM ranked WHERE rn=1 ORDER BY customer_id;
```

预期 `(102,1,100,1),(104,2,NULL,2),(105,3,80,1)`。最新订单不一定金额最高；客户 1 两笔金额并列第一，但唯一 ID 让“最新一笔”确定为 102。窗口层不能用同层 WHERE rn=1 替代外层过滤。

### 推演 5：降序游标下一页

```sql
-- 第一页为 105、104；游标来自 104，而非客户端当前时间。
SELECT id FROM drill_order
WHERE created_at<'2026-10-03'
   OR (created_at='2026-10-03' AND id<104)
ORDER BY created_at DESC,id DESC LIMIT 2;
```

预期 `103,102`。建议实验索引 `(created_at,id)`，再加入百万行比较与大 OFFSET 的计划及扫描成本。新增更晚订单通常不会挤入此游标后的页，但修改排序字段可能造成跨页遗漏或重复。

### 推演 6：含 NULL 的 NOT IN

```sql
CREATE TABLE drill_blocked(customer_id INT NULL);
INSERT INTO drill_blocked VALUES (2),(NULL);
SELECT id FROM drill_customer
WHERE id NOT IN (SELECT customer_id FROM drill_blocked) ORDER BY id;
SELECT c.id FROM drill_customer c
WHERE NOT EXISTS (SELECT 1 FROM drill_blocked b WHERE b.customer_id=c.id)
ORDER BY c.id;
```

第一个查询无结果；第二个为 `1,3,4`。先手推 id=1 的每次比较，再解释 NOT 与 UNKNOWN；不要把 NOT IN 和 NOT EXISTS 在可空数据上的语义一律当作等价。

### 推演 7：条件更新维护库存不为负

```sql
CREATE TABLE drill_stock(sku_id INT PRIMARY KEY, available INT NOT NULL);
INSERT INTO drill_stock VALUES (1,1);
UPDATE drill_stock SET available=available-1 WHERE sku_id=1 AND available>0;
SELECT ROW_COUNT(); -- 1
UPDATE drill_stock SET available=available-1 WHERE sku_id=1 AND available>0;
SELECT ROW_COUNT(); -- 0
SELECT available FROM drill_stock WHERE sku_id=1; -- 0
```

两个会话并发执行时，一方可能等待，最终最多一次成功扣减。该条件只保护单次库存更新，不防同一请求多次购买其他仍有库存的商品；订单与请求唯一约束仍需另加。

### 推演 8：一对多连接重复累计

```sql
CREATE TABLE drill_item(id INT PRIMARY KEY, order_id INT NOT NULL, line_amount INT NOT NULL);
INSERT INTO drill_item VALUES (1,101,60),(2,101,40);
SELECT o.id,SUM(o.amount) AS wrong_total
FROM drill_order o JOIN drill_item i ON i.order_id=o.id
WHERE o.id=101 GROUP BY o.id;
SELECT o.id,o.amount,s.line_total
FROM drill_order o JOIN
 (SELECT order_id,SUM(line_amount) AS line_total FROM drill_item GROUP BY order_id) s
 ON s.order_id=o.id WHERE o.id=101;
```

前者错误地得到 `(101,200)`；后者得到 `(101,100,100)`。`SUM(DISTINCT amount)` 不是通用修复：不同订单完全可以合法具有相同金额，按金额去重会少算。先确定粒度，再连接已聚合的明细。

### 推演 9：连续日期与重复登录

```sql
CREATE TABLE drill_login(customer_id INT NOT NULL, login_date DATE NOT NULL);
INSERT INTO drill_login VALUES
 (1,'2026-10-01'),(1,'2026-10-02'),(1,'2026-10-02'),
 (1,'2026-10-04'),(1,'2026-10-05'),(1,'2026-10-06'),
 (2,'2026-10-03'),(2,'2026-10-04');
WITH days AS (
 SELECT DISTINCT customer_id,login_date FROM drill_login
), numbered AS (
 SELECT customer_id,login_date,
 ROW_NUMBER() OVER(PARTITION BY customer_id ORDER BY login_date) AS rn
 FROM days
), islands AS (
 SELECT customer_id,login_date,DATE_SUB(login_date,INTERVAL rn DAY) AS island
 FROM numbered
)
SELECT customer_id,MIN(login_date),MAX(login_date),COUNT(*) AS consecutive_days
FROM islands GROUP BY customer_id,island HAVING COUNT(*)>=3
ORDER BY customer_id,MIN(login_date);
```

预期只有 `(1,2026-10-04,2026-10-06,3)`。用户 1 的前两天形成长度 2 的另一段，重复登录不增加天数；用户 2 只有两天。把日期减行号的中间表先写出来，是判断算法而非背模板的关键。

## L4 · 并发、恢复与取舍演练

1. 两会话验证 RC/RR：A BEGIN 后先读，B 更新并提交，A 再读；然后把 A 第一次读改到 B 提交后。参考：是否建立过快照比 BEGIN 时间更关键；不要把锁定读混进普通快照的推理。
2. 两账户反向加锁构造死锁，保存持有/等待关系并统一加锁顺序。参考：牺牲哪个事务不应写死；应用要恢复完整业务事务且不重复外部副作用。
3. 为一次在线加索引列出临时空间、元数据锁、回滚条件和验证 SQL。参考：执行计划改善与写入回归都要验收。
4. 对订单库设计备份恢复和分片迁移，模拟切换后新侧收到一笔订单再回退。参考：必须处理这笔增量，不能只把流量切回旧库。
