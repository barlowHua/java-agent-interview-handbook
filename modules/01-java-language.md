# 01 Java 语言与代码设计

> 优先级：P0。学习基线：Java 17/21；Java 8 仅作遗留系统对比。L1～L4 表示掌握深度，不对应公司职级。建议学习 3 次，每次 60～90 分钟。

## 学习目标与前置

能解释一段代码为何这样运行，能把语言规则转成可靠的业务接口。前置是实际写过 Java 服务。第一遍读 L1 与核心题，第二遍写练习，第三遍结合项目回答 L3。面试参考答案应按自己的语速补充例子，目标是 60～90 秒讲清结论、机制、场景与限制，不必逐字背诵。

## L1 必会：类型、对象和资源

Java 始终按值传递。基本类型复制数值；引用类型复制引用值，因此方法内改变对象内容会被调用者观察到，重新给形参赋值不会改变调用者变量。`final List<String>` 禁止引用重新赋值，却不禁止 `add`。所谓不可变对象，还要求内部状态不能通过别名被修改、构造时不泄漏 `this`，必要时防御性复制。

`==` 对引用比较身份；`equals` 表达领域相等。相等对象必须有相同 `hashCode`，相同哈希不代表相等。领域建模先定义身份：订单通常用稳定订单号，金额通常要包含币种。不要把可能变化的名称、状态加入哈希键。包装类型比较用 `equals` 或转换为明确的基本类型，不能依赖整数缓存；自动拆箱前要处理 `null`。

异常也是接口设计。参数非法、业务拒绝、依赖超时与代码缺陷应区分，转换异常时保留 cause。文件、连接、流用 try-with-resources；关闭顺序与声明顺序相反，关闭异常可出现在 suppressed 中。不能在 `finally` 中返回结果覆盖原异常。捕获 `InterruptedException` 后应传播，或恢复中断标记并结束当前任务。[语言类型规则](https://docs.oracle.com/javase/specs/jls/se21/html/jls-4.html)

## L2 原理：泛型、分派与不可变性

泛型主要提供编译期约束，擦除后类型变量通常变为上界，编译器补必要的类型转换和桥接方法。擦除不等于 class 文件没有任何泛型信息：方法、字段的声明签名可保留元数据，反射可以读取；普通对象不能因此直接回答完整的运行时类型参数。`List<Integer>` 不是 `List<Number>`，否则可以向整数列表放入小数。生产者用 `? extends T` 读取，消费者用 `? super T` 写入；读取消费者通常只能安全视为 Object。

重载在编译期按声明类型选择，重写在运行期根据接收对象实际类型分派。静态方法属于类，不能把隐藏当重写；字段也没有实例方法那样的多态。理解这一点能解释代理、序列化和框架反射遇到的“明明实现了却没调用”。

字符串不可变利于共享和哈希键稳定，但不意味着字符串内容适合长期保存秘密。大量循环拼接通常用局部 `StringBuilder`，不能把 JDK 8 的编译策略直接当作所有版本的实现。Stream 是延迟执行的流水线，终结操作触发计算；带状态、有副作用的 lambda 会让并行与重试难以推理。先写可理解的普通循环，再考虑是否需要 Stream。

## L3 工程：把语言规则用于业务契约

金额要明确精度、币种、舍入位置和溢出规则。`new BigDecimal("0.1")` 直接表达十进制输入；`new BigDecimal(0.1)` 会反映二进制浮点值的近似。`compareTo` 按数值比较，`equals` 还比较 scale，所以 `1.0` 和 `1.00` 在 HashSet 和 TreeSet 中可能表现不同。统一表示应在业务边界完成，不能在任意层悄悄四舍五入。[BigDecimal API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/math/BigDecimal.html)

接口返回集合时明确“不可修改视图”“独立副本”“元素不可变”三件事。`Collections.unmodifiableList(source)` 仍会观察到底层列表后续变化；`List.copyOf(source)` 隔离列表结构，但不会深拷贝其中的可变元素。日志、缓存和异步任务对可变对象的延迟读取，可能记录到请求结束后的状态，必要时先构建不可变快照。

设计一个服务类时，先列出它保护的业务不变量，例如“退款总额不能大于实付额”，再决定由哪层校验和哪种并发控制维护。不要把所有校验散落在 Controller，也不要为每个实体机械生成接口与实现。可测试的边界来自职责清楚、依赖显式以及副作用集中。

## L4 拓展：版本与边界

P1：掌握 Java 17 中已正式提供的 record、sealed class，及 Java 21 的 switch 模式匹配、record pattern。record 适合表达数据载体，但仅提供浅不可变语义；其组件是可变列表时仍需防御性处理。sealed 约束可继承范围，可以帮助穷尽处理状态。P2：模块系统、反射开放边界、MethodHandle；遇到强封装问题先检查库兼容性，避免永久堆积 `--add-opens`。[Record 语言指南](https://docs.oracle.com/en/java/javase/21/language/records.html)

## 机制图解：引用复制与对象共享

![Java 值传递：修改共享对象与重新绑定形参的区别](assets/01-value-passing.svg)

**读图顺序：** 先看两个面板顶部的变量，再沿箭头看它们指向哪个对象。调用发生时，`order` 的引用值被复制到 `p`，两个变量并不因此变成同一个变量。左图执行 `p.status = PAID`，修改的是共同引用的 A；右图执行 `p = new Order()`，只有 `p` 改指 B。把方法参数声明为 `final` 只会禁止右图中的重绑，不会禁止左图中的对象修改。

**记忆点：** 变量保存值，引用值指向对象；复制引用不复制对象，修改对象不等于修改调用方变量。一次浅拷贝又多了一层区别：`new ArrayList<>(source)` 创建新列表，但两个列表的元素仍可能指向同一批对象。

**图中未覆盖的边界：** 这是语言语义图，不是对象在物理内存中的地址图；JIT 可能消除分配。它也没有建立任何跨线程同步关系：两线程共享对象以后，仍需按第 03 章考虑安全发布与并发修改。数组、集合、record 组件都遵守相同的引用规则。[JLS：方法调用中的参数赋值](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.12.4.5)

**闭卷重画：** 调用方持有 `List<Order>`，方法先复制列表，再修改第一个订单的状态，最后给形参重新赋值。请画出每一步的变量、两个列表和订单对象，并标出调用方最终能观察到的变化。

### 从图走向 API 设计

| 接口承诺 | 实现方式举例 | 仍要检查的边界 |
| --- | --- | --- |
| 禁止调用方通过返回值增删元素 | `Collections.unmodifiableList(source)` | 底层列表仍可变，元素也可能可变 |
| 列表结构与输入隔离，返回列表不可修改 | `List.copyOf(source)` | 不是深拷贝；不接受 null 元素 |
| 调用方无法改变返回对象的业务状态 | 转为不可变值对象并复制嵌套可变成员 | 日期、数组、集合及嵌套对象都要检查 |

面试时不要只回答“加 final”。给出一个具体反例，例如 `record Report(List<Order> orders)`：组件引用不能重新赋值，但其中订单仍可能修改。说明防御性复制的范围与成本，才算把语言特性落实到接口契约。[List.copyOf 契约](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/List.html#copyOf(java.util.Collection))

## 六道核心题与追问

### 1. Java 为什么是值传递？

**60～90 秒参考答案：** 方法调用把实参的值复制给形参，引用本身也是一个值。假设调用者持有一个订单对象，方法拿到的是指向同一对象的引用副本，因此修改订单状态能被调用者看到；但方法将形参指向新订单，只改变局部变量。理解这一点后，才能判断 API 是否会修改输入，以及异步任务是否与调用者共享状态。需要隔离时要明确复制深度，不能认为传参已经复制对象。

**追问：** 传入集合后想保证调用方不受影响？**要点：** 复制集合结构；若元素可变还需复制元素或转换为不可变值对象；明确成本与契约。

### 2. equals 和 hashCode 怎么设计？

**60～90 秒参考答案：** 先定义业务相等，再实现方法。equals 应满足自反、对称、传递、一致和对 null 为假；相等对象的哈希必须相等。哈希集合先定位桶再做相等判断，所以只重写 equals 会破坏查找契约。参与相等与哈希的字段最好稳定，例如订单号；把状态作为哈希字段后再改状态，会出现元素还在集合里却找不到。继承层级也要防止父子类的相等判断不对称。

**追问：** 数据库主键未生成前能否用实体做 Set 键？**要点：** 注意多个 null 主键被误判相等以及入集合后主键变化；优先稳定业务键或明确实体身份生命周期。

### 3. 泛型擦除后还有什么意义？

**60～90 秒参考答案：** 泛型把很多错误前移到编译期，减少显式强转，并让 API 表达生产和消费关系。运行时通常使用擦除后的类型，编译器会补类型检查所需的转换，重写泛型方法时可能生成桥接方法。因此不能直接创建 `new T()`，也不能把 `List<Integer>` 当作 `List<Number>`。声明处的泛型签名可能仍保留，框架可以通过反射读取，这与每个普通对象携带完整类型参数是两回事。

**追问：** `List<? extends Number>` 为什么不能加入 Integer？**要点：** 实际列表可能是 `List<Double>`；除了 null，没有可保证安全的具体元素类型。

### 4. 怎样实现真正可用的不可变对象？

**60～90 秒参考答案：** 不可变是对象对外可观察状态不再变化。字段 final 只是起点，还要控制继承、构造期间不泄漏 this，并保护内部可变成员。输入列表在构造时复制，输出不能泄漏可变引用；嵌套元素可变时，浅复制仍不够。不可变对象让缓存、并发共享和故障重放更容易推理，但大对象频繁整体复制有成本，可以按业务边界拆分。record 能减少样板代码，却不会自动深拷贝组件。

**追问：** 不可变是否等于无需安全发布？**要点：** 正确构造的 final 字段有特殊可见性保证，但容器、引用更新和其他共享状态仍需正确同步与发布。

### 5. 业务异常怎么分层？

**60～90 秒参考答案：** 我按调用者能采取的动作分类：输入不合法需要修改请求，业务拒绝需要展示原因，暂时性依赖故障可能重试，代码缺陷应报警。异常要保留原始原因并带业务上下文，跨接口转成稳定错误码，避免泄露内部细节。不会统一 catch Exception 后返回成功，也不会在每层重复记录同一异常。是否重试还要看操作幂等、总时限和错误类型，不能因为是运行时异常就一律重试。

**追问：** 关闭资源失败时原业务异常会消失吗？**要点：** try-with-resources 保留主要异常，关闭异常进入 suppressed；普通 finally 写法可能覆盖，需检查异常链。

### 6. 金额为什么不用 double？

**60～90 秒参考答案：** 很多十进制金额不能被二进制浮点精确表示，直接运算可能影响相等判断和累计结果。常见选择是最小货币单位整数，或有明确 scale、舍入规则的 BigDecimal。前者简单但要防溢出和多币种精度，后者灵活但不能忽略构造方式、除法舍入以及 equals 与 compareTo 的差别。业务上要规定是逐项舍入还是汇总后舍入，并用能暴露分摊尾差的案例验证总额守恒。

**追问：** 100 元分给三个人怎么办？**要点：** 明确分摊顺序、最小单位、剩余一分的归属以及重试结果确定性，不只回答保留两位小数。

## 常见误区

- “final 就是不可变”“StringBuilder 绝对比 + 快”“Stream 一定更快”都忽略使用方式。
- 把受检异常与可恢复、运行时异常与不可恢复机械对应，忽略业务语义。
- 用实体所有字段生成 equals/hashCode，未考虑持久化生命周期。

## 练习与参考验证

用 `record Money(String currency, BigDecimal amount)` 建模，并实现三人分摊。先规定 CNY 使用分、输入拒绝超过两位有效小数、分摊按收款人稳定排序。验证：100.00 的结果为 33.34、33.33、33.33；总和等于原值；重复执行结果一致；零金额合法；负数按明确的退款契约处理或拒绝；不同币种不能相加。再用可变 List 作为另一个 record 的组件，演示浅不可变问题并以 `List.copyOf` 修复结构共享。这里给出验收条件，不宣称已经运行你的实现。
