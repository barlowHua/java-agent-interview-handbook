## L1～L4 专题问答

### Q1：BeanFactory、ApplicationContext 和作用域各解决什么问题？

**参考回答：** BeanFactory 提供对象定义、创建和依赖获取的基础能力，ApplicationContext 在此基础上组织应用上下文，并提供事件、资源等应用级支持。singleton 是每个容器中每个定义的共享实例，不是 JVM 全局唯一，更不等于线程安全；prototype 按获取创建实例，但注入到单例的普通依赖通常只在创建单例时解析一次。需要每次调用得到新对象时，应显式使用 provider 或合适作用域代理，并理解谁关闭资源。请求作用域还依赖请求上下文，不能随意在异步线程使用。选作用域要从状态所有权和生命周期出发。

**深入追问：** prototype 对象谁调用销毁回调？**答案要点：** 容器通常不负责完整销毁，需要使用方安排；不能因为注解写了作用域就默认资源会自动关闭。

### Q2：构造器注入为什么能更早暴露循环依赖？

**参考回答：** 构造器注入要求创建对象前就具备必要依赖，所以 A 构造需要 B、B 构造又需要 A 时，没有一个完整实例可先提供，通常无法直接完成。属性注入可以先创建实例再填充依赖，在允许循环引用且满足范围等条件下，容器可能通过提前引用处理部分循环，但这并不使相互依赖的职责设计自然合理。优先寻找可抽出的第三种职责、单向接口或事件边界，延迟代理只能改变获取时机，不能消除所有逻辑循环。回答时还需区分 Framework 机制与 Boot 项目的默认循环引用策略。

**深入追问：** 给其中一个依赖加 Lazy 就彻底解决了吗？**答案要点：** 可能延后解析，但若构造或初始化时立即调用仍可能触发问题；运行时依赖方向与失败责任也未因此改善。

### Q3：单例三级缓存的目的是什么，为什么不能套用于所有循环？

**参考回答：** 常见 Spring 单例创建流程区分完成的单例、提前暴露的对象引用和可生成提前引用的工厂。第三层工厂给框架机会在确实需要提前引用时结合后处理器生成一致的引用，例如涉及自动代理的场景，而不是一开始就把裸对象无条件发布出去。它依赖对象至少已经实例化，所以不能直接解决互相等待构造参数的循环；prototype 和复杂代理组合也有边界。理解重点是最终注入的引用与对外暴露对象是否一致，以及提前对象尚未完成初始化的风险。具体缓存名称是源码细节，不是业务可以依赖的稳定协议。

**深入追问：** 把未初始化对象注入另一个 Bean 有何风险？**答案要点：** 对方若在初始化阶段立即调用它，字段与不变量可能尚未就绪；能创建成功不等于所有初始化行为正确。

### Q4：FactoryBean 与普通的 Bean 工厂方法有什么区别？

**参考回答：** FactoryBean 是容器支持的一种工厂对象契约，容器按普通名称获取时通常返回其生产的对象，而不是工厂本身；需要工厂对象时使用相应的特殊获取语义。它适合创建方式复杂或需要代理包装的对象，产品的类型与单例属性由契约参与描述。普通 Bean 工厂方法则是一个创建定义的来源，不能只因名字有 Factory 就等同。生命周期上还要区分工厂 Bean 和产品对象，产品缓存与销毁不能照抄普通单例的全部假设。排查类型匹配与自动注入时，要确认查询到的究竟是哪一层对象。

**深入追问：** FactoryBean 产品一定是单例吗？**答案要点：** 不是，要看 isSingleton 等契约和容器处理；不能把工厂自身为单例推导成每次产品引用必定相同。

### Q5：BeanFactoryPostProcessor 与 BeanPostProcessor 为什么不能混用？

**参考回答：** 前者主要修改 BeanDefinition 等容器元数据，后者围绕已创建实例的生命周期参与处理，二者作用时机和目标不同。例如替换配置值适合定义处理阶段，自动代理则需要根据实例包装暴露对象。依赖注入和生命周期注解还由相关后处理器扩展参与，不是一个固定的大反射步骤。定义处理器若过早主动获取普通 Bean，可能使对象提前实例化，错过后续正常扩展机会，因此应保持职责清楚。自己写后处理器要控制匹配范围、顺序和幂等性，避免对全部对象递归创建依赖或重复包装。

**深入追问：** 能否在 BPP 中对每个对象随意调用 getBean？**答案要点：** 可能引入提前初始化、循环与处理顺序问题；依赖应最小化且理解创建阶段，不把容器扩展当普通业务服务调用。

### Q6：Configuration 的代理与 proxyBeanMethods=false 有何影响？

**参考回答：** 完整配置类可以通过生成的子类拦截配置方法之间的调用，使对另一 Bean 方法的调用遵守容器管理的对象语义。关闭方法代理或采用轻量模式后，这种同类 Java 调用通常就是普通方法调用，可能重新执行工厂方法而得到额外对象，并不自动返回容器里的同一个单例。因此配置依赖更清楚的写法是把依赖声明为 Bean 方法参数，由容器注入，避免依赖方法拦截。关闭代理可以减少不需要的增强，但前提是没有依赖这类跨方法调用语义；不能只为启动优化机械修改所有配置类。

**深入追问：** 两个 Bean 方法都调用 `client()` 时怎样验证？**答案要点：** 对比容器中 client 与两个服务实际持有引用的身份，并记录构造次数；不要只检查 BeanDefinition 数量。

### Q7：AOP 多个切面的顺序为什么可能改变事务和重试语义？

**参考回答：** 多个增强形成拦截器链，进入与退出的嵌套顺序决定谁覆盖谁的执行范围。重试包在事务外通常可以让每次尝试进入新的事务边界，而事务包在重试外可能让多次尝试共享同一事务状态，第一次失败后已回滚标记也可能影响后续。日志、鉴权、缓存同样会受顺序影响，不能只看注解都存在。应明确切点、顺序和代理层次，画出一次成功与失败的调用栈，再用事务结果验证。不要依赖同一切面中多个同类型增强的隐含发现顺序，也不要把业务正确性隐藏在难以观察的代理组合里。

**深入追问：** 缓存命中绕过目标方法会有什么影响？**答案要点：** 内层事务、指标或鉴权增强可能不执行，取决于链顺序；安全与业务边界应明确，不能假定所有注解每次都运行。

### Q8：Spring Boot 自动配置的入口、条件和退让机制如何解释？

**参考回答：** 自动配置通过版本对应的导入机制加载候选配置，再根据类路径、属性、应用类型与已有 Bean 等条件选择生效内容。Boot 3 的自动配置候选注册不能简单照搬老版本只说 spring.factories；编写自定义 starter 时应按对应版本使用自动配置导入文件。常见 missing-bean 条件允许用户定义覆盖默认装配，但并非所有配置都有相同条件。排错先看依赖树、候选导入、条件评估报告和 Bean 定义，再定位哪个条件不成立。组件扫描与自动配置是相关但不同的机制，扩大扫描范围未必能修复条件失配。

**深入追问：** 为什么依赖存在但 Bean 仍没出现？**答案要点：** 还可能缺属性、应用类型不符、被已有 Bean 排除、被显式禁用或导入注册错误，使用条件报告逐项验证。

### Q9：外部化配置、Profile 与配置绑定怎样排查？

**参考回答：** 配置值来自多个来源并按规则覆盖，Profile 决定哪些配置参与，不等于拥有任意最高优先级。实际值异常时，要定位属性来源、激活配置、环境变量命名转换和绑定类型，而不是只检查仓库里的 application 文件。成组配置可用 ConfigurationProperties 表达类型并校验必需值，避免大量散落字符串；敏感值应从合适的秘密管理来源获取，诊断输出要脱敏。不同启动方式、测试注入和命令行参数可能改变最终值，升级时需核对版本文档。动态刷新也不是所有 Bean 属性天然重新绑定的保证。

**深入追问：** 为什么测试环境正确、生产却连接错数据库？**答案要点：** 对齐实际启动参数、环境变量、配置中心和 Profile，检查最终属性来源；仅比较同名 YAML 文件不足以证明配置一致。

### Q10：Qualifier、Primary 和条件装配如何避免“注错实现”？

**参考回答：** 按类型注入只是候选解析起点，多个候选时还要结合限定条件、优先标记、名称等规则。Primary 表达默认优选，但不意味着任何集合注入都只保留它；Qualifier 更适合把业务语义表达成明确限定，而不是依赖碰巧的字段名。条件装配又受到定义可见时机影响，不能假设任意配置声明顺序都等价。工程上给多实现命名有语义的边界，例如主库和报表库，并在启动验证实际绑定。依赖必须显式时使用构造器，不应通过允许覆盖同名 Bean 来掩盖冲突，避免升级后悄悄换实现。

**深入追问：** 注入 `List<Strategy>` 时 Primary 会筛掉其他实现吗？**答案要点：** 一般不会按单值优选那样筛掉其余候选；集合候选和排序需按对应注入契约处理。

### Q11：事务传播的逻辑作用域和物理事务如何区分？

**参考回答：** 每次被拦截的事务方法可以形成逻辑作用域，但 REQUIRED 常让多个逻辑作用域共用一个物理事务。REQUIRES_NEW 则独立开启物理事务并暂挂外层资源，内层提交可以在外层失败后仍保留；它还可能增加连接需求和锁等待。NESTED 常基于同一物理事务的保存点局部回滚，外层最终回滚仍会撤销整体，且支持取决于管理器。其余传播规则也应围绕是否允许已有事务来解释，例如 MANDATORY 要求已有、NEVER 拒绝已有。先定义业务原子边界，再选传播，不能用独立事务掩盖所有错误。

**深入追问：** 内层 REQUIRES_NEW 写外层锁住的同一行会怎样？**答案要点：** 可能等待外层，而外层又同步等待内层完成；独立事务不代表没有资源依赖，可能超时或出现更复杂锁冲突。

### Q12：UnexpectedRollbackException 与 catch 的关系是什么？

**参考回答：** 共享物理事务时，内层事务逻辑可能在异常经过自己的拦截器后将事务标为 rollback-only，外层 catch 只能改变业务控制流，不能自动擦掉这个标记。外层正常返回时仍尝试提交，框架用 UnexpectedRollbackException 让调用者知道最终并未提交，防止“方法成功返回就误以为数据成功”。需要区分异常被内部完全吞掉、异常越过内层代理和数据库本身已使事务不可继续等情况。修复应调整业务边界、异常契约或保存点方案，不能只再次 catch 提交异常后向调用方返回成功。

**深入追问：** self-invocation 的内层抛异常被 outer catch，一定标回滚吗？**答案要点：** 内层未经过事务拦截时不能套该推理；还需检查外层最终异常及数据库是否标记事务失败。

### Q13：事务的 readOnly、隔离级别和 timeout 能保证什么？

**参考回答：** readOnly 通常向事务管理器、驱动或 ORM 传达只读意图，具体优化与强制行为依赖实现，不能当鉴权禁止写入。隔离级别限定数据库并发观察语义，是否应用取决于是否创建了新的物理事务，加入已有事务时不会凭内层声明就自动重建隔离级别。timeout 也不等于所有远端调用和任意 Java 代码都能被强制停止，需确认事务管理器如何传递到具体资源。设计应把数据库事务尽量缩短，外部 I/O 自有超时预算，使用真实数据库验证读写与锁行为，而不是只查看注解参数。

**深入追问：** 外层 READ_COMMITTED，内层 REQUIRED 写 SERIALIZABLE 是否升级？**答案要点：** 加入同一物理事务通常不会升级；可配置校验拒绝不兼容声明，或调整边界，不能误认注解覆盖已运行事务。

### Q14：多数据源中的事务管理器怎样影响原子性？

**参考回答：** 一个本地事务管理器通常只协调其对应资源，给方法加事务注解不意味着所有数据源和远端操作都自动纳入同一原子提交。必须明确选择哪个管理器、DAO 从哪个数据源拿连接、是否通过事务感知的路径获取，以及动态路由发生在连接获取前还是后。多库写入若需要一致结果，要讨论支持条件下的分布式事务，或采用状态机、outbox、补偿和对账形成业务保证。盲目嵌套两个本地事务可能出现一边已提交另一边失败。面试要能描述具体失败窗口和恢复责任，而不是只说切换数据源注解即可。

**深入追问：** 事务中切换路由键为何可能没换数据库？**答案要点：** 连接可能已绑定在当前事务资源中，后续继续复用；必须检查路由与获取连接的实际时机及代理顺序。

### Q15：怎样写能证明事务行为的集成测试？

**参考回答：** 事务测试要检查最终数据而不只看方法抛异常。准备真实数据库或足够一致的测试实例，通过真实容器代理调用被测服务，制造可控失败，再在被测事务结束后用独立连接查询结果。测试方法自身被事务包裹并自动回滚时，可能改变传播环境并掩盖真实提交，异步线程更不一定属于测试事务。应分别覆盖默认运行时异常、受检异常规则、自调用、共享回滚标记、独立事务和保存点；记录实际事务管理器与线程。不同数据库的锁和隔离行为还要在目标数据库上复核，不能只靠内存数据库通过。

**深入追问：** 使用抢占式测试超时有什么风险？**答案要点：** 测试代码可能被放到另一线程，偏离测试框架绑定的事务上下文；需要核对工具行为，避免误以为所有写入都会自动回滚。

### Q16：一次 Spring MVC 请求怎样从入口走到响应？

**参考回答：** 请求先经过 Servlet 容器相关过滤器链，再到 DispatcherServlet。它通过 HandlerMapping 找处理器及拦截器，通过合适的 HandlerAdapter 调用处理器；方法参数由解析器等完成绑定，业务调用后由返回值处理和消息转换器或视图解析生成响应。异常可能由异常解析器处理，不能把全部错误都当 Controller 方法内部返回。链路中还存在过滤器短路、拦截器拒绝、参数校验失败和异步处理分支。排错时沿请求经过的最深阶段定位，区分路由未匹配、参数无法解析、业务失败和序列化失败，避免只在 Controller 加日志。

**深入追问：** 为什么 HTTP 400 时业务方法根本没进入？**答案要点：** 参数绑定、消息反序列化或校验可能在方法执行前失败；需看对应异常解析及请求内容类型。

### Q17：Filter、Interceptor 和 AOP 的边界怎样选择？

**参考回答：** Filter 位于 Servlet 请求处理链，能包装请求响应并覆盖到达它的多种 Servlet 请求；MVC Interceptor 围绕映射到的处理器执行，可以看到处理器信息，但不等于所有网络请求的统一边界；AOP 面向被代理对象的方法调用，与 HTTP 请求不必一一对应。选择取决于责任：协议层处理可放过滤器，处理器相关观察可用拦截器，服务方法的事务和指标可用切面。鉴权宜使用成熟的统一安全链，不能仅凭 MVC 拦截器假设覆盖所有路径。异步分派和错误分派还可能改变回调次数，需要按实际契约测试。

**深入追问：** Interceptor 的 afterCompletion 是否覆盖全部 Filter 失败？**答案要点：** 不覆盖从未进入对应处理器执行链的请求；清理责任必须放在真正拥有该资源的层级与 finally 路径。

### Q18：消息转换、参数校验与字段安全有什么联系？

**参考回答：** 消息转换器把请求体与 Java 类型互换，选择受到内容类型、接受类型和配置影响；参数绑定与校验则负责把输入解释成业务可接受的形式。DTO 不应直接暴露持久化实体的全部可写字段，否则可能允许客户端修改不该控制的状态。格式正确不等于业务合法，跨字段和状态相关规则仍需业务层验证。错误响应应包含稳定错误码和可用字段信息，同时避免泄漏内部类型及栈。序列化还要关注循环引用、大对象、时间和金额表示以及未知字段策略，升级时保留协议兼容测试。

**深入追问：** Valid 验证通过能否省掉库存或权限检查？**答案要点：** 不能；结构和字段约束不替代并发条件更新、资源权限和业务状态机，尤其不能防止检查后状态变化。

### Q19：统一异常处理怎样避免“所有错误都返回 200”？

**参考回答：** 统一处理应把内部异常转成稳定的接口语义，同时保留合适 HTTP 状态、业务错误码、请求关联标识和服务端诊断信息。参数错误、未授权、资源不存在、冲突与依赖故障需要不同处理，不能为了前端方便一律返回成功状态，否则监控、代理和客户端重试都会误判。ControllerAdvice 等机制也有覆盖边界，过滤器、安全链或响应已提交后的错误未必由同一路径解决。日志应在负责诊断的边界记录，避免每层重复打印；敏感输入和完整异常栈不应直接发给客户端。重试建议还要结合幂等和期限。

**深入追问：** 响应已经开始流式输出后抛异常怎么办？**答案要点：** 可能无法再修改状态与普通错误体；需要协议内错误/终止语义、连接清理与独立监控，不能假设全局处理器能重写一切。

### Q20：MyBatis 的占位参数与字符串替换为什么不同？

**参考回答：** `#{}` 通常生成预编译参数占位并由类型处理器绑定值，数据库将其作为数据处理；`${}` 把内容直接拼入 SQL 文本，若来源可被用户控制就可能改变语法。表名、列名和排序方向不能简单当普通值占位，所以动态标识符需要从服务端固定白名单映射，不能直接接受客户端片段。参数绑定也不意味着整条 SQL 自动安全，其他拼接点、动态脚本和权限过滤仍要检查。日志可能显示带值 SQL 只是展示方式，不等于实际使用字符串拼接。应覆盖引号、空集合与非法排序字段的用例。

**深入追问：** `ORDER BY #{column}` 能安全选择任意列吗？**答案要点：** 绑定的是值而非 SQL 标识符，语义通常不符合动态列名要求；使用枚举或白名单选择预先写好的列表达式。

### Q21：ResultMap、TypeHandler、动态 SQL 和 null 参数如何避免隐患？

**参考回答：** ResultMap 明确结果列与对象结构的映射，复杂关联应标清身份列，避免重复行合并错误或字段覆盖；TypeHandler 负责 Java 与 JDBC 类型之间的转换，适合受控值对象、枚举和特殊类型。动态 SQL 的 if、where、set、foreach 改变实际语句形态，空集合、全空更新和可空条件都要明确定义，不能生成没有 WHERE 的批量更新。null 参数有时需要明确 JDBC 类型，具体取决于驱动与配置。调试既要看绑定参数，也要看最终 SQL 和结果映射，不能把所有问题归因于数据库返回错了。

**深入追问：** `ids` 为空应该返回所有数据还是零条？**答案要点：** 先定义业务契约，通常应显式拒绝或返回空结果；不能因 foreach 被跳过而无意去掉过滤条件。

### Q22：SqlSession、Mapper 代理和 Spring 事务如何协作？

**参考回答：** MyBatis 的 Mapper 代理把接口方法映射到语句执行，实际仍依赖 SqlSession、执行器和数据库连接。普通 SqlSession 不应跨线程共享；Spring 集成常通过线程安全的 SqlSessionTemplate 按当前事务管理会话和异常转换，不能因此把底层任意会话都当线程安全。事务管理器使用的数据源必须与 SqlSessionFactory 的数据源正确对应，才能共享同一事务资源。使用 Spring 管理的会话时不要手工提交或关闭来破坏容器协议；若绕开集成自行创建会话，需要自行负责事务和资源生命周期。代理对象安全不代表 SQL 业务操作天然幂等。

**深入追问：** 异步线程拿同一个 Mapper 引用是否共享外层事务？**答案要点：** 引用可复用不等于事务上下文跨线程传播；异步调用按其执行线程资源处理，应明确自己的事务边界。

### Q23：MyBatis 一级和二级缓存为什么可能影响一致性？

**参考回答：** 一级缓存通常与 SqlSession 的本地执行上下文关联，默认作用域和清理时机会影响同会话重复查询；二级缓存需要配置，通常按 namespace 等边界组织，并有提交与失效规则。它们不会自动感知所有其他应用或任意 SQL 对同表的修改，因此跨命名空间关联查询与外部写入可能带来过期结果。缓存还可能保留对象引用，修改返回对象要理解是否影响随后读取。需要严格新鲜度时，应明确缓存范围、失效责任和会话边界，并通过不同事务、不同会话验证，而不是看到少发一次 SQL 就认定优化安全。

**深入追问：** 开启二级缓存后同表的所有 Mapper 会一起失效吗？**答案要点：** 不能默认；缓存按配置边界组织，需检查 cache-ref、命名空间与修改语句清理规则，也考虑外部写入。

### Q24：分页、N+1 和联表映射应怎样避免隐藏的放大？

**参考回答：** N+1 是先查一批主记录，再为每条记录单独查关联，网络往返和数据库负担随条数增长；延迟加载只是改变触发时机，遍历时仍可能全部发生。可以使用批量查询、适当联表或分阶段组装，但一对多联表会放大行数，直接在联表结果上分页可能截断主记录集合。分页还要区分框架内存跳过、插件改写 SQL 和数据库真正限制，观察最终 SQL 与执行计划。深分页可考虑稳定排序的游标方案，并设计唯一次级键和并发更新语义，不能只加一个分页插件就保证性能与结果正确。

**深入追问：** 查询 20 个订单及全部明细怎么分页？**答案要点：** 可先按稳定顺序取 20 个订单主键，再批量取明细并组装；控制第二次查询规模，定义两次查询的一致性要求。

### Q25：批量执行、乐观锁和受影响行数怎样形成正确写入协议？

**参考回答：** 批量执行可能把语句积累到 flush 或提交阶段才真正发送，因此错误出现时点、返回计数和生成主键获取方式不能照搬逐条执行。批次大小要受内存、包大小、锁持有和失败恢复成本约束，并明确部分失败时整体回滚还是分批提交。乐观锁通常在 WHERE 中包含版本号，更新成功再增加版本，必须检查实际受影响行数；零行不一定只是并发冲突，也可能记录不存在或条件不匹配。重试需重新读取业务状态并保证外部副作用幂等，不能只机械重复旧 SQL。MyBatis 不会自动替所有语句提供完整乐观锁协议。

**深入追问：** BATCH 模式下能立即用 mapper 返回值判定版本成功吗？**答案要点：** 不能不经确认就当最终行数；需要检查 flush 后批处理结果与驱动语义，关键条件更新可选明确的即时执行方式。

### Q26：MyBatis 插件拦截哪些边界，为什么顺序和缓存键很重要？

**参考回答：** MyBatis 插件围绕支持的内部接口与指定方法形成拦截，例如 Executor、StatementHandler、ParameterHandler 和 ResultSetHandler 的相关操作，不是任意 Mapper 方法都能靠同一签名直接拦截。分页、租户条件、审计与加密等插件可能改写 SQL、参数或结果，多层代理的顺序会改变实际行为。尤其是改 SQL 却未同步考虑参数映射、查询缓存键和计数语句，可能得到错误结果或跨租户污染。应限制匹配范围，保证调用链继续执行和异常释放，固定版本并通过最终 SQL、绑定值及缓存隔离测试验证，不能仅以插件方法被调用作为成功证据。

**深入追问：** 分页插件与租户插件都改写 SQL，应验证什么？**答案要点：** 主查询与 count 查询都包含正确租户条件，分页语义一致，参数顺序和缓存键隔离正确；用两个租户的相同参数制造反例。

## 代码审查与真实数据库练习

下面 SQL 片段表达参数绑定与条件更新。它是 Mapper 内的示意片段，需要配置实际数据源、Mapper 接口和数据库后运行，不宣称本手册已替你完成数据库验证。

```xml
<update id="reserve">
  UPDATE inventory
  SET available = available - #{quantity}, version = version + 1
  WHERE sku = #{sku}
    AND version = #{version}
    AND available &gt;= #{quantity}
</update>
```

调用前校验 quantity 必须为正，数据库表设置合适非负约束（依目标数据库支持情况）和唯一 SKU；检查受影响行数恰为 1。事务中再写预订单，使用稳定请求号唯一约束处理重试。若使用批处理执行器，先解释为何不能把即时返回值直接当最终行数。

完成四组验证：两个并发事务抢同一版本时最多一个成功；预订单写失败时库存修改回滚；同请求号重复请求不重复扣库存；业务方法改为 this 自调用后，按真实外层事务重新预测结果。查询最终状态使用受测事务结束后的独立连接，同时记录 SQL、事务管理器、线程和异常。

容器练习：各建一个有方法代理和无方法代理的配置类，让两个 Bean 工厂方法调用同一个 client 工厂，比较真实对象身份；再改为方法参数注入，验证依赖稳定。Web 练习：分别制造路由缺失、JSON 格式错误、校验失败、业务异常、序列化异常，记录它们是否到达 Controller，以及最终 HTTP 状态与错误码。
