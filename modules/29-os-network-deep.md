# 29｜操作系统、网络与 RPC 深挖

优先级 P0/P1。前置：[10 请求链路](10-network-os.md)。本章覆盖进程线程、调度、内存、IO、TCP、HTTP、TLS、DNS、RPC、连接池、流式接口。平台行为以目标 Linux/协议版本为准，不把命令输出跨操作系统套用。

## L1 基础：把概念放回层次

应用层有 HTTP/RPC 与业务消息；传输层有 TCP/UDP；操作系统管理 socket、缓冲区、进程和调度；运行时又叠加 Java 线程、事件循环与对象内存。同一个“慢”可以发生在不同层，先建立层次再谈优化。

## L3 深入问答

### Q1：进程、线程和协程如何区分？

**参考回答：**进程提供资源和地址空间边界，线程是进程中的执行单元，共享部分进程资源但有独立执行栈与状态。协程或虚拟线程由运行时在较少系统线程上调度，降低等待执行单元的管理成本，但不凭空增加 CPU。比较时我会分开隔离、切换成本、阻塞行为和调度方式；Java 虚拟线程、平台线程与其他语言协程不能只按名字等同。

**追问：一个线程崩溃会只影响自己吗？** 普通未捕获 Java 异常可能结束该线程；native 崩溃、进程级终止或共享状态损坏可能影响整个进程，须说明故障类别。

### Q2：用户态、内核态与上下文切换是一回事吗？

**参考回答：**用户态和内核态体现执行权限边界，系统调用让内核替应用完成受控操作。进入内核不一定切换到另一个任务；上下文切换是调度另一执行上下文，需要保存恢复状态。阻塞 IO 可能先进入内核，再因等待被调度出去。分析开销时要区分系统调用次数、任务切换、缓存失效和实际等待，不能把它们都算作一次固定成本。

**追问：减少线程就能减少延迟吗？** 可能减少抢占，也可能使 IO 等待期间没有足够并发，需要结合任务类型与排队结果测量。

### Q3：虚拟内存、页表与缺页是什么？

**参考回答：**进程使用虚拟地址，页表等机制将其映射到物理页并施加保护。缺页异常表示当前访问需要内核处理映射或页面，不一定意味着从磁盘读数据；按需分配、写时复制、页面已在缓存但未映射都可能触发。虚拟地址空间很大不意味着已占用同样多物理内存。分析进程内存需要区分映射、驻留、共享和容器记账口径。

**追问：minor fault 与 major fault？** 通常区分处理是否需要从存储读取页面，但应结合平台统计与负载，不能只看计数认定故障。

### Q4：为什么 fork 看起来复制进程，却没有立即复制所有内存？

**参考回答：**常见实现利用写时复制，让父子进程先共享物理页，任一方写入时再复制相应页面。这降低初始成本，但 fork 仍有页表等开销；后续写入频繁时会增加实际内存。像持久化子进程场景，不能只观察 fork 瞬间，而要覆盖整个子进程存活期间的写压力和内存峰值。

**追问：容器剩余内存少时有什么风险？** 父子进程的新增页面与运行时开销可能超出限制，即使最初 RSS 看起来可控，也需用代表性写负载验证。

### Q5：页缓存、用户缓冲区和直接内存如何区分？

**参考回答：**页缓存由操作系统管理文件数据；用户缓冲区位于应用可访问内存；Java 直接缓冲区通常使用堆外内存。它们可能参与同一次读写，但管理者与回收时机不同。减少拷贝不等于不用内存，堆外增长也不能仅靠 Java 堆直方图解释。排查时结合 JVM 内存、进程 RSS、文件缓存和容器统计，避免把共享页简单重复相加。

**追问：mmap 就没有 IO 成本吗？** 仍涉及缺页、缓存、写回与存储延迟，收益依赖访问模式和实现。

### Q6：阻塞、非阻塞、同步、异步 IO 怎么说清？

**参考回答：**阻塞描述调用在条件未满足时是否等待，非阻塞通常返回当前无法完成的状态；同步/异步还要看谁完成数据操作、如何通知完成，术语应结合具体 API。就绪通知告诉应用可以尝试读写，不保证整个业务消息完成；完成通知表达某个提交的操作已结束。面试最好用具体 socket 或文件 API 说明，而不是背四象限却混淆语义。

**追问：使用 epoll 就没有阻塞了吗？** epoll_wait 自身可阻塞等待事件；处理线程也可能在错误放入的业务调用上阻塞。

### Q7：select、poll、epoll 的关键差别是什么？

**参考回答：**它们都能监视多个 IO 描述符的就绪状态。select 和 poll 的接口以及集合处理方式不同；epoll 维护注册关系和就绪事件集合，常适合大量连接且少量活跃的场景。不能简单宣称所有 epoll 操作 O(1) 或任何负载都更快，因为注册、事件数量和应用处理仍有成本。选型还受平台支持与框架封装影响。

**追问：边缘触发为什么容易漏处理？** 若收到通知后未读到 EAGAIN 就再次等待，缓冲区仍有数据却可能没有新边缘；通常结合非阻塞 IO 正确排空并保存处理状态。[epoll 手册](https://man7.org/linux/man-pages/man7/epoll.7.html)

### Q8：Reactor 与 Proactor 区别在哪里？

**参考回答：**Reactor 通常围绕就绪事件调度处理器，由处理器执行读写；Proactor 通常围绕异步操作完成通知组织后续处理。真正的框架可能混合模型。设计重点是事件线程不能被慢业务长期占住，转移执行器时应控制队列、上下文、回调顺序和错误传播。模型名称不能替代对操作系统 API 和线程使用的实际观察。

**追问：Netty 一个连接始终由一个 EventLoop 处理就线程安全吗？** 只限定部分事件执行；共享业务状态、外部执行器和跨 Channel 访问仍可能并发。

### Q9：TCP 三次握手为什么不能简单减成两次？

**参考回答：**连接建立需要双方确认通信能力、序列号与连接状态，第三次确认让服务端知道自己的信息被对端接收。讨论两次握手要同时考虑历史报文、重传和双方状态，不能只背“确认收发能力”而不解释状态推进。SYN 洪泛、半连接队列与 SYN cookie 等属于实现与防护层，配置要按内核和负载核对。

**追问：服务端 SYN-ACK 丢了？** 客户端尚未完成建立，双方会按重传和超时规则推进；业务尚不能据此认为连接已可正常使用。

### Q10：流量控制与拥塞控制解决什么不同问题？

**参考回答：**流量控制避免发送方压垮接收方，典型依据接收窗口；拥塞控制避免网络路径过载，调整发送行为。有效发送还受应用供数、窗口和网络条件共同限制。慢接收者、网络丢包和服务端业务处理慢可能表现相似，要结合窗口、重传、RTT 与应用指标判断。不能用无限扩大 socket 缓冲区解决所有吞吐问题。

**追问：接收窗口为零怎么办？** 按协议处理窗口探测和恢复，应用还要判断为何未及时消费，不能只重建连接绕开背压。

### Q11：粘包、半包为什么是应用协议问题？

**参考回答：**TCP 提供字节流，发送两次不保证接收也分成两次。应用需用长度字段、分隔符或固定长度等规则恢复消息边界，处理跨读取和多消息合并。长度字段还要限制最大值、防止溢出和恶意分配；分隔符需要转义与编码规则。UDP 保留报文边界，但有大小、分片和丢失方面的不同约束，不能简单认为更省事。

**追问：长度头只收到一半呢？** 保留解析状态，等后续字节足够再读取正文，不把一次 read 的长度当完整消息长度。

### Q12：HTTP 缓存的强缓存和协商缓存怎么工作？

**参考回答：**新鲜响应可按缓存规则直接使用；需要重新验证时，可以带条件头由服务端判断资源是否变化。ETag 与 Last-Modified 是常见验证器，304 让客户端复用已有内容，而不是重新返回完整正文。还要考虑 Cache-Control、Vary、认证请求和共享缓存边界。缓存键漏掉租户或内容协商条件会产生串数据风险。

**追问：no-cache 等于不保存吗？** 不是，通常要求使用前重新验证；no-store 才表达不要存储的要求，仍需理解具体缓存遵循情况。[HTTP 缓存 RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html)

### Q13：HTTP/1.1、HTTP/2、HTTP/3 的队头阻塞有何不同？

**参考回答：**HTTP/1.1 的请求组织和连接使用可能让后续响应等待；HTTP/2 在连接中复用多个流，缓解应用层组织限制，但 TCP 丢包恢复仍可能影响连接上的多个流。HTTP/3 基于 QUIC，流之间的传输恢复边界不同。协议优化不消除服务端排队、连接级流控和共享资源瓶颈，实际收益需结合代理与客户端部署验证。

**追问：HTTP/3 完全没有队头等待？** 不应这样绝对表述；同一流、应用依赖和共享容量仍会导致等待。

### Q14：DNS 修改后为什么有的用户仍访问旧地址？

**参考回答：**DNS 解析涉及多层缓存与 TTL，应用或运行时还可能有自己的地址缓存策略，已有长连接也不会因记录变化立即重连。排查要比较权威结果、递归解析、客户端实际地址与连接生命周期。迁移时留出新旧地址共存和健康检查窗口，不能把 TTL 当作全球同一时刻切换的保证。

**追问：TTL 设很小就万无一失？** 会增加解析压力，也不能消除已有连接和不按预期缓存的客户端行为。

### Q15：HTTPS 到网关终止后，内网调用天然安全吗？

**参考回答：**TLS 只保护它覆盖的连接段。网关终止后到服务的传输、服务身份和调用权限仍需按威胁模型设计。mTLS 可帮助双向认证，但有证书不等于有业务对象权限；证书发行、轮换、吊销和服务身份映射也需要管理。不能把“内网”当所有请求可信，也不能把加密传输当作敏感日志的保护。

**追问：TLS 1.3 0-RTT 适合任意写操作吗？** 应考虑重放风险与应用语义，不能直接用于没有幂等和重放防护的重要副作用。[TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html)

### Q16：连接池越大，吞吐越高吗？

**参考回答：**池把并发与资源复用联系起来。池太小会排队，太大可能把数据库或远端压满并增加上下文切换。先估算到达率、持有连接的平均时长和下游容量，再看获取等待、活跃数、超时与尾延迟。长事务和事务内远程调用会延长持有时间，通常应先缩短占用，再决定是否扩池。

**追问：最大连接数如何分给多个实例？** 以数据库总预算扣除管理与其他服务余量，再按实例数和扩容峰值分配，不能每台各自取最大值。

### Q17：负载均衡后某台机器特别忙，原因有哪些？

**参考回答：**先区分请求数量不均、请求成本不均和机器能力不均。长连接复用、会话黏性、热点租户、不同实例预热、局部下游慢都可能产生偏斜。轮询不保证工作量均匀；按活跃请求或延迟选节点也会受采样和反馈延迟影响。结合每实例流量、耗时分布、连接数和资源判断，避免盲目重启热点实例导致缓存更冷。

**追问：一致性哈希能解决吗？** 能控制部分重映射并保持亲和，但热点 key 仍可能集中，需额外拆分或隔离。

### Q18：SSE、WebSocket 和轮询怎么选？

**参考回答：**轮询实现简单但有延迟和空请求；SSE 适合服务端向客户端持续推送文本事件；WebSocket 适合双向交互。还要考虑代理缓冲、断线恢复、心跳、身份过期和慢消费者。LLM 流式输出不仅是文本分片，还应表达工具开始/完成、取消和最终状态，客户端关闭不表示远端副作用被撤销。

**追问：流断了怎样续传？** 需要稳定任务 ID、事件序号和可恢复状态；没有持久事件或重放协议就不能宣称无缝续传。

### Q19：用哪些证据区分 CPU、锁和 IO 问题？

**参考回答：**CPU 用热点采样、线程时间和 GC 数据；锁看等待栈、持有者与持续时间；IO 看连接/磁盘延迟、队列和下游状态。多个指标沿同一时间窗口关联，单次线程转储不能证明长期热点。先用低成本数据缩小范围，再选择 JFR、堆转储或更细采样，诊断本身也有资源和隐私成本。

**追问：线程是 RUNNABLE 就是 CPU 瓶颈？** 不一定，运行时状态与底层阻塞并不总是一一对应，需要 CPU 时间和栈共同判断。

### Q20：容器 CPU 受限时，为什么宿主机空闲仍会慢？

**参考回答：**容器可能受到 cgroup 配额、调度竞争或其他资源约束，宿主机总平均空闲不能说明该进程可以随意使用 CPU。分析时看实际配额、节流时间、可用处理器识别和线程池设置，结合请求排队与延迟。内存也要分清 Java 堆和容器总计费，避免只调 Xmx 而忽略直接内存与线程栈。

**追问：直接增加副本呢？** 可能改善局部 CPU，却可能耗尽数据库连接或上游配额，需要全链路容量验证。

## L4 练习、边界与过关

构造三个假设：事件线程被阻塞、数据库连接长时间未归还、DNS 切换但长连接未释放。分别写出最少两个区分证据与一个止损动作。参考：线程栈与事件处理延迟；借出连接时长与锁等待；解析结果与实际远端地址。没有这些证据，不要把相关性当根因。

过关：20 题能随机接两层追问；能用图定位“不确定结果”的位置；知道哪条命令/指标属于哪一层。内核调优、eBPF 开发和协议证明属于岗位专项，本文不替代完整系统课程。
