# 33｜系统设计案例：把机制串成可落地的方案

> P0；Agent 专项案例为 P1。每个案例都是自设面试练习，不是任何公司的真实架构。数字用于演算，必须先明确口径，再根据实际岗位调整。先完成 [11 系统设计](11-system-design.md) 与 [09 分布式](09-distributed.md)。

## L1｜统一答题框架

1. 澄清用户行为、核心不变量、规模、延迟、可用性、合规与成本约束。
2. 算平均/峰值流量、存储、带宽和并发，标明是假设还是已知数据。
3. 定义 API、数据主键、状态机与事务边界，画出读写路径。
4. 讨论热点、幂等、顺序、一致性、超时未知、降级和恢复。
5. 给出可观测指标、压测/故障验收与演进方案。

不要一上来写几十个中间件名字。先让最小方案在约束下成立，再针对证据扩展。

## L3｜完整案例与参考方案

### Q1：设计短链接服务，重点是什么？

**参考回答：**先约定创建和跳转、有效期、可修改性、反滥用及统计要求。假设每天新增 100 万条、峰值跳转 2 万次/秒，平均创建约 11.6 次/秒；每条含索引预算按 500 B 估算，逻辑年增约 182.5 GB，副本和备份另算。API 为 `POST /links` 与 `GET /{code}`；主表 `code UNIQUE, destination, owner, expiry, status`。编码可用足够随机空间并依靠唯一约束重试，或全局 ID 后 Base62；不可预测需求不能只靠短编码。跳转走缓存、主库回源并处理过期和封禁，记录点击可异步、允许明确范围的统计延迟。301/302 等状态应根据可修改性和缓存策略选择，否则客户端缓存可能绕过后续封禁。热点链接可多级缓存，但缓存失效与恶意 URL 审查必须可追踪。

**追问：随机生成永远不会冲突吗？**不会保证；先估算碰撞概率，再由唯一约束检测和有限重试兜底。编码空间、请求量和攻击可猜测性分别讨论。验收覆盖重复创建、并发碰撞、封禁传播与缓存击穿。

### Q2：设计秒杀库存，怎样保证不超卖？

**参考回答：**先区分抢购资格、库存预留、订单成功、支付成功。假设库存 1 万、入站峰值 10 万 QPS，入口先按商品和用户限流，避免把全部流量推给数据库；排队返回受理状态，不等于下单成功。核心不变量是可用库存非负、同一用户资格最多一次、同一订单只预留一次。小规模可用 `UPDATE stock SET available=available-1 WHERE sku=? AND available>0` 加唯一业务约束，在本地事务创建预留与订单。规模更大可分库存桶或使用受控预扣，但必须说明唯一事实来源和故障对账，不能把 Redis 成功当永久成交。支付、取消通过条件状态迁移，超时释放与支付回调竞争时以持久化状态为准；重复回调不重复扣减或释放。

**追问：Redis 预扣成功后服务宕机？**预扣凭据和订单要有可恢复映射；根据业务权威状态重试或释放。仅加一个过期时间无法证明没有丢单。验收包括重复请求、超时取消与付款竞争、消息重放和库存守恒对账。

### Q3：设计支付与退款编排，如何面对“结果未知”？

**参考回答：**在自己控制的边界建立支付单与唯一商户请求号，状态至少区分待发起、处理中、成功、明确失败和待确认。调用第三方超时只能说明没拿到响应，不能立即判失败并换新单重试。用同一幂等号查询或重试，回调验签并校验商户、金额、币种和订单关联，结合版本/条件更新实现单向合法状态迁移。账务流水使用独立唯一事件标识，业务状态和账务写入的事务边界必须说明；跨服务通过可靠事件和对账补齐。退款是独立操作与状态机，在同一原子边界校验“已成功退款 + 已预占额度（含处理中/UNKNOWN）+ 本次申请 ≤ 实收金额”，并立即为本次申请预占，避免两笔并发都看见成功额为零而超退。明确失败才释放预占，成功则把预占转为已退；不能因请求超时释放。金额用最小货币单位整数或精确十进制，记录币种与舍入规则。

**追问：第三方查询说不存在，可以重新支付吗？**需核实其查询一致性与请求幂等契约，不存在可能是暂时未可见。先保留 UNKNOWN 并走确认流程，不能据一次查询创造重复扣款。验收重放回调、金额不符、迟到成功、并发退款和跨日对账差异。

### Q4：设计即时消息，送达和顺序怎样定义？

**参考回答：**先区分服务器已持久化、对端设备已收到、用户已读，三个状态不能共用一个 ACK。客户端发送带 `clientMessageId`，服务端在会话维度去重并分配序号，持久化成功后返回受理确认；通过连接网关投递在线设备，离线设备按游标拉取。顺序通常承诺会话内而非全局，重连时依据已确认游标补拉，客户端按 messageId 去重。网关保存连接路由但不作为消息唯一存储，多设备需明确各自 ACK 与用户已读语义。大群广播可分批扇出，设置背压与慢连接清理；附件放对象存储，消息仅引用有权限的资源。

**追问：先收到序号 103 再收到 102 怎么办？**可短暂缓冲并补拉缺口，超过预算展示同步中或采用明确弱顺序语义。不能把网络投递顺序当作用户最终读取顺序。验收覆盖断线重连、网关迁移、重复投递和游标持久化失败。

### Q5：设计关注 Feed，推模式还是拉模式？

**参考回答：**首先明确时间排序还是推荐排序、可见性与删除要求。推模式在作者发布时写入关注者收件箱，读快但大 V 扇出极大；拉模式读取时合并关注作者内容，写轻但读成本和延迟较高。可按粉丝数与活跃度混合：普通作者推，超大作者读时拉取，再按排序键合并去重。收件箱保存引用和必要排序信息，正文独立存储；权限与删除状态仍在读时复核。分页用稳定游标，例如时间加唯一 ID；推荐排序需要固定会话快照或明确可能变化，不能保证 offset 翻页无重复遗漏。

**追问：用户取关后收件箱已有内容怎么办？**定义立即不可见还是允许短暂滞后；需要即时不可见时读时校验关系，后台清理历史引用。验收热门作者发布、批量取关、内容封禁和跨页去重。

### Q6：设计延迟任务/定时调度系统，如何避免重复执行？

**参考回答：**定义一次性或周期任务、时间精度、时区、允许误差与错过触发策略。持久化任务表含 nextRunAt、状态、版本、租约持有者与到期时间；调度器分片扫描到期任务并以条件更新领取，任务量大时结合时间桶或时间轮减少扫描成本。到期唤醒机制不是事实来源，宕机后要能从持久化状态恢复。执行端记录 attempt 与业务幂等键，外部副作用采用幂等协议或结果查询。租约过期允许新执行者接手，但旧执行者可能仍在运行，关键资源需 fencing 或业务条件防旧写入。

**追问：Exactly once 调度可保证吗？**通常只能在限定数据库状态变更边界做到一次；任意外部效果需协议配合。说明至少一次执行加业务去重及未知结果处理。验收时钟偏移、调度器暂停、租约续约失败和周期任务积压。

### Q7：设计大文件上传和异步导出，怎么恢复与控制资源？

**参考回答：**上传先授权创建会话，限制大小和类型，按分块签发短期受限上传凭证，记录 uploadId、块序号与校验值，完成阶段校验块集合和总校验后发布文件元数据。客户端重试同一块应幂等，未完成碎片由生命周期策略清理；下载入口再次检查访问权。若返回对象存储预签名 URL，它就是持有即可使用的临时凭证，应用 ACL 撤销不会自动使已签 URL 失效；短 TTL 仍有窗口，要求即时撤权时应使用下载代理或存储层可执行的授权策略。导出则创建可查询状态的任务，记录查询条件快照或数据水位，分页/流式读取并写对象存储，限制租户并发与内存。任务状态区分排队、运行、完成、失败、取消，工作进度可恢复。完成通知只是提示，文件链接需短期有效且与权限关联，并说明已发链接和已开始下载的撤权限制。

**追问：导出过程中数据在变，如何保证一致？**明确快照导出或允许变化；长事务快照成本较高，可按版本水位、离线副本或预计算实现。单纯 keyset 分页解决效率，不自动提供整份导出的一致快照。

### Q8：设计统一限流与 API 网关，什么应该留在业务服务？

**参考回答：**网关承担协议入口、路由、基础认证、配额、请求大小、超时与可观测关联。按租户、用户、接口及成本建立限流键，令牌桶控制平均速率并允许突发，并发限额控制在途资源，两者可以组合。单节点本地限流便宜但全局额度近似；集中限流更准确却引入网络延迟和依赖，应定义存储故障时 fail-open 还是 fail-closed。网关传递可信身份需要防伪造，业务服务仍做对象、字段、状态与租户权限检查。重试只允许可重试类型，传递 deadline 和幂等键，避免网关与服务多层放大。

**追问：给所有接口一样的 QPS 上限好吗？**不同接口成本差异很大，下载、搜索、LLM 生成可按并发、token或权重配额控制。验收包括单热点租户、限流依赖故障及拒绝请求是否仍消耗昂贵资源。

### Q9：设计搜索/报表数据链路，如何保证可重建？

**参考回答：**交易库是约定的事实来源，搜索索引或报表宽表是派生视图。以全量快照加增量变更流构建，记录快照与日志的衔接水位，消费按主键和版本幂等更新，处理删除墓碑、重复与乱序。先建立新索引，追平增量并抽样/全量校验后切换别名，保留回滚窗口。读接口说明刷新延迟与一致性边界，关键刚写后的状态可回源权威存储。报表聚合需要定义事件时间、处理时间、迟到与修正策略；数据“最终一致”必须有延迟指标和修复责任。

**追问：重建时继续消费旧 topic 就一定无丢失吗？**需证明日志保留覆盖重建窗口，快照水位正确且消费无缺口；如果 CDC 位点已过期，必须重新建立可靠基线。验收重建中断、schema变更和删除事件丢失。

### Q10：设计企业知识问答与可执行 Agent 平台，边界在哪里？

**参考回答：**分离知识问答与执行工具两条路径。资料进入解析、分块、版本与权限标记、索引，查询先绑定租户身份再检索与重排，生成答案带可追溯引用并允许拒答。执行 Agent 用持久化任务状态管理规划、工具调用、审批、确认与恢复；模型提出动作，确定性策略检查主体、资源、参数和预算后才执行。只读工具与写工具分级，写操作有幂等号和结果查询，超时进入 UNKNOWN。保存提示/模型/索引/工具版本以便复现，原文和轨迹按敏感级别脱敏。按真实任务集评估成功率、越权率、人工介入率、P95 与成功任务成本，灰度时保留回滚到较简单工作流的能力。

**追问：何时上多 Agent？**当独立子任务、权限隔离或可并行评估带来可测收益时再引入；给出单 Agent/固定工作流基线、协调成本与失败恢复对比。验收包括恶意文档、跨租户检索、重复工具调用、取消与审批过期。

## L4｜容量演算与验收练习

用案例 Q2 演算：入站 10 万 QPS 不等于成功写入 10 万 QPS。假设入口放行 5000 QPS、订单处理平均 80 ms，稳定状态平均在途约 `5000×0.08=400`；这只是 Little 定律下同一边界的平均值，不能直接当线程数或 P99 容量。若每订单写 3 行，存储写压力还要考虑索引、日志、复制与失败重试。

用 Q10 演算：每天 2 万任务，平均输入 4000 token、输出 800 token、平均模型调用 2 次，则粗估输入 1.6 亿、输出 3200 万 token/日；实际必须按每轮上下文累计，不能把最初用户输入当全部输入。价格使用选定供应商当期单价，此资料不固化会过期价格。

**过关标准：**任选一个案例，45 分钟内完成需求假设、数量级、数据模型、主链路与三个故障窗口；另用 10 分钟接受“规模十倍、预算减半、权限即时撤销”之一的变更。交付一页 ADR 和故障测试表，不能只交架构图。
