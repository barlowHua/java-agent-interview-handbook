# 15｜LLM 基础：从模型机制到服务接口

目标：能把一次模型请求解释到 token、推理、输出校验和成本；能判断问题该交给模型、检索还是业务代码。前置：HTTP、概率基础、向量点积、服务延迟与缓存。建议用两次学习完成：先口述，再手算和设计。

资料核对：2026-10-04。这里讲通用 Transformer 与自回归推理原理；不固定商业模型的价格、上下文长度和排行榜。API 支持的参数、JSON Schema 子集及计费口径必须随所选模型版本核验。

## L1｜必须能口述

LLM 根据已有上下文预测后续 token。它把训练中学到的统计规律用于生成，不能把流畅回答直接视为事实证明。token 是分词器的编码单位，不等于一个字或单词；同一句话在不同分词器下长度可能不同。上下文通常包含系统要求、用户消息、历史消息、工具定义和工具结果，并要为输出保留空间。

模型调用可以承担理解、分类、抽取、生成和提出工具调用；工具执行、身份校验、金额计算、数据库提交仍由应用承担。一次正确的工程流程是：构造输入 → 调模型 → 识别完成/拒绝/截断/工具调用 → 校验结构与业务条件 → 执行动作或返回结果。

**复述骨架：概率生成不是事实库；上下文是有限预算；结构正确不等于语义正确；工具调用提议不等于获得执行权限。**

## L2｜理解机制

### 1. Transformer 与推理阶段

嵌入层把 token 编号映射成向量。注意力通过 Query、Key、Value 计算位置之间的关联，再与前馈网络等模块组合；自回归生成采用因果约束，使当前位置不能读取未来 token。多头注意力可以表达不同关联，但不能简单把某个头解释成固定语法规则。[原始论文](https://arxiv.org/abs/1706.03762)

![从 token 编号、QKV 与因果掩码到下一个 token 的机制图](assets/15-token-attention.svg)

**读图顺序：**先从左上读到右上，再沿右侧进入注意力，经过中间的汇总与输出；左下三角矩阵解释因果掩码。当前位置 i 可以使用位置 j≤i 的表示来预测后续 token，不能偷看未来输入。

**关键记忆点：**单头注意力可写为 `A = softmax(QKᵀ/√dₖ + M)`、`输出 = A V`。Q 是当前表示提出的匹配条件，K 用于被匹配，V 是被加权汇总的信息；`dₖ` 是每头 Q/K 的维度，缩放防止点积量级随维度增长过大；M 在允许位置为 0，在屏蔽位置为负无穷，使其权重为 0。softmax 按每个查询位置的候选键归一化。它表达信息聚合，不是把相关位置判定为“正确答案”。

**简化边界：**图中是解码器自注意力主干，省略归一化与具体位置编码实现；原始 Transformer 还包含编码器和交叉注意力，不能把该图当成所有模型的完整结构。模型内部的 token embedding 与为搜索训练的文本 embedding 是不同用途，也不必使用同一个模型。

**闭卷重画：**只给四个位置，画出因果掩码并说明为什么第 2 行不能看到第 4 列；再画出 K 与 V 分别进入哪一步。参考验证：未来位置被屏蔽的是注意力得分，不能把 V 整体清零或把所有历史 token 删除。

Prefill 处理输入上下文，建立后续生成需要的中间状态；decode 逐步生成新 token。KV cache 保存先前位置的 Key/Value，减少后续步骤重复计算，但会占用显存，并随序列和并发增长。它不是存储最终答案的业务缓存。分页管理可改善 KV 内存利用率，实际吞吐取决于硬件、模型、批处理和负载。[PagedAttention 论文](https://arxiv.org/abs/2309.06180)

首 token 时间 TTFT 包含排队、网络及首段推理等因素；总响应时间还受输出长度、工具调用和多轮循环影响。流式返回改善感知等待，不代表计算更少；独立请求并行可以缩短关键路径，却可能提高瞬时资源需求。[延迟优化](https://developers.openai.com/api/docs/guides/latency-optimization)

![Prefill 产生首个 token，后续 decode 读取并追加 KV cache 的时序机制图](assets/15-prefill-decode.svg)

**读图顺序：**上排从输入到 prefill 与首 token；下排看缓存如何进入 decode，再沿紫色回路理解逐步生成。两个缓存箭头分别表示读取旧 KV 和追加新 KV。

**关键记忆点：**标准自回归实现中，prefill 的末位输出就可以用于预测首个新 token；生成后续 token 时才依次处理刚产生的 token。因果约束不意味着 prefill 必须逐个串行计算所有输入位置。KV cache 缓存已经处理过的位置，不是把最终回答存下来，也通常不需要缓存所有历史 Q。

**简化边界：**图示省略连续批处理、分块 prefill、推测解码与多卡切分。KV 粗略字节数 `2×L×T×Hkv×dh×b` 中，2 表示 K 与 V，L 是层数、T 是缓存长度、Hkv 是 KV 头数、dh 是每头维度、b 是每元素字节数；这是单序列、常规全注意力下的量级估算，不包含权重、激活、碎片或复制。跨请求前缀复用还依赖匹配与隔离条件，不能仅凭语义相似就复用。[vLLM 前缀缓存设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)

**闭卷重画：**画出“长输入短输出”和“短输入长输出”可能分别慢在哪里。参考验证：标出排队、TTFT 与完整响应三个不同观察点；同一请求内的 KV 复用与跨请求前缀缓存要分开说。

### 2. Embedding 与生成不是一回事

Embedding 把文本表示为向量，便于相似检索和聚类；相似度描述表征空间的接近程度，不是“这段文档正确的概率”。余弦相似度是点积除以向量模长乘积。需要核验归一化、距离函数、维度，以及查询和文档使用的模型是否兼容。替换嵌入模型通常要重建文档向量，并验证新旧索引迁移。[嵌入文档](https://developers.openai.com/api/docs/guides/embeddings)

### 3. 结构化输出的三道门

普通 JSON 输出先解决能否解析；受约束的结构化输出进一步约束字段、类型和枚举，但支持范围因 API 而异。应用仍需处理拒绝、截断和失败，再检查引用是否存在、订单是否属于当前用户、金额是否超限等业务条件。解析成 Java DTO 只跨过了其中一道门。[结构化输出](https://developers.openai.com/api/docs/guides/structured-outputs)

### 4. 采样、停止与可复现

模型输出词表 logits 后，通常经 softmax 形成下一 token 的分布。temperature 在常见实现中缩放 logits，较低值通常让高概率候选更占优势；top-k 保留固定数量候选，top-p 保留累计概率达到阈值的一组高概率候选，再重新归一化采样。具体组合顺序、参数范围及是否可用由服务实现决定，不能假设每个模型都接受相同参数。它们改变生成分布，不会补足缺失知识。

停止条件可能是结束符、长度上限、用户取消或预算耗尽，要保留完成原因；截断的 JSON 不能当完整业务结果执行。固定 seed 与较低温度也不是跨模型版本、硬件与并行实现逐字一致的保证。复现评测需保存模型版本、输入、参数和运行配置，业务正确性最终仍由证据与执行结果验证。

## L3｜面试题与参考表达

下面每题按“结论 → 机制 → 工程例子 → 边界”练习，连同追问约 60～90 秒；先脱稿说，再对照补漏，不要求逐字背诵。

### Q1：LLM 为什么会幻觉？降低 temperature 能解决吗？

**参考回答：**LLM 的训练目标与事实核验不同，它会生成在上下文里合理的续写。知识缺失、提示歧义、检索错误和推理失误都可能产生无依据答案。降低 temperature 通常降低采样多样性，却不会补足证据，也不能保证每次输出完全一致。我会先按错误来源分类：事实查询补充可靠检索，精确运算调用确定性工具，缺失必要信息则澄清或拒答；然后对事实正确性、引用支持度和任务完成分别评测。业务不能仅凭模型自报的信心决定是否执行。

**追问：有引用就可信？**不一定。引用可能存在，但并不支持具体断言；要检查来源时效、权限、引文位置及断言与证据的一致性。

### Q2：上下文很长，是不是可以把所有资料放进去？

**参考回答：**窗口长度只是容量上限，不是有效利用能力的保证。大量无关内容会增加成本和首 token 延迟，还可能稀释关键证据；历史中的错误也会被重复带入。我会给指令、当前问题、事实状态、检索证据和输出分别分配预算，保留关键约束与来源，只压缩可恢复的历史。摘要会丢信息，因此订单号、用户授权和已完成动作要存成结构化状态，并按需读取原文。资料规模大或权限复杂时，仍需检索和过滤，不能只依赖长上下文。

**追问：压缩后如何继续？**保存摘要版本、原消息引用和未完成步骤；恢复时重新校验过期状态，不能把摘要中的推测提升成事实。

### Q3：prefill、decode、KV cache 与性能有什么关系？

**参考回答：**Prefill 消化输入，decode 基于已有上下文逐步生成。KV cache 复用先前位置的注意力状态，减少重复工作，但也使长序列和高并发消耗更多显存。排查慢请求时我先看排队、TTFT、每 token 延迟和工具耗时，而不是只看总时长。输入很长可能拖慢首包，输出很长可能拖慢完整回答，多轮工具调用则会叠加请求开销。我会按瓶颈选择缩短输入、限制冗余输出、减少轮次或优化并发，再测质量是否退化。

**追问：缓存命中等于不用推理？**不等于。前缀缓存可能减少部分输入计算，后续新输入与生成仍需工作；它也不等于业务答案缓存。

### Q4：embedding 能直接解决搜索问题吗？

**参考回答：**Embedding 解决一种语义表示问题，不负责整个检索系统。它适合寻找同义表达，但订单号、错误码、版本号等精确条件可能更适合关键词或结构化查询。我会根据问题类型路由，组合词法召回和向量召回，并把租户、权限、有效时间作为过滤条件。检索质量用标注集的 Recall@K 和排序指标验证，不能把某个余弦分数当作通用阈值。换模型时需要评估领域语料、维度、向量兼容性和索引迁移成本。

**追问：向量维度越高越好吗？**不是单调关系。维度增加存储与检索成本，效果要用同一任务集实测，不能跨模型只比较维度。

### Q5：结构化输出与 function calling 怎么选？

**参考回答：**如果目标是把抽取结果返回程序，例如发票字段，我优先选择支持的结构化输出并映射成 DTO；如果模型需要读取订单或执行动作，就给它明确的工具定义。两者都可能使用 schema，但目的不同：一个约束结果格式，一个表达可调用能力。应用需要处理工具参数、调用结果和继续推理的循环。无论哪种方式，模型输出都必须经过服务端验证，不能让它自己声明用户身份或管理员权限，也不能把生成出的 SQL 直接交给高权限连接。

**追问：JSON 合法但金额错误怎么办？**再做领域校验：币种、精度、上限、订单剩余额度；金额来自账务系统，模型负责解释而不是最终记账。

### Q6：RAG、微调和提示词优化分别解决什么？

**参考回答：**提示词优化先明确任务、约束和示例，适合低成本验证能力；RAG 在请求时提供外部证据，适合知识更新、引用和文档权限；微调调整任务行为或输出习惯，是否有效要看数据质量和评测。它们可以组合，但不能把微调当作可靠实时数据库，也不能期待 RAG 自动修复所有推理错误。我会先做可测基线，把失败分成知识缺失、检索失败、行为不稳定和工具错误，再选择改动。训练数据必须与独立测试集隔离，避免只提升见过题目的分数。

**追问：模型不知道公司规定，先微调？**先验证检索能否提供正确且当前有效的规定。只有稳定行为缺口且有足够高质量数据时，再评估微调。

### Q7：Java 工程师选模型最该看什么？

**参考回答：**先定义任务和约束，而不是从榜单选最强模型。我要看业务成功率、工具选择和参数正确率、结构输出支持、延迟分位数、成本、上下文需求及部署约束。使用同一组真实脱敏任务，记录模型版本、提示词、数据和参数；对难题、无答案、超时、拒绝等分桶。简单分类可用规则或小模型，复杂规划再升级。路由也会出错，因此要把路由成本与误判纳入总评估，最终比较每个成功业务任务的总成本。

**追问：大模型兜底能保证质量吗？**不能；它可能共享相同知识缺口。兜底必须有触发条件、总预算、独立验证以及人工接手出口。

## L4｜边界拓展与设计练习

**容量题：**假设教学模型窗口为 32,000 token，系统与工具定义 4,000，历史 8,000，预留输出 4,000，保留安全余量 2,000，则检索预算最多 14,000。这里只是加法示例；实际还要核验消息封装、多模态和推理 token 的供应商口径，不能把字符数代入。

**延迟题：**模拟请求排队 0.3 秒、prefill 0.8 秒、生成 600 token 且 50 token/秒、单次工具 0.4 秒，总量级约 13.5 秒；如果改成两轮，每轮都有额外推理，不能只加工具时长。验证时用 trace 看关键路径，不能把不同请求的 p95 直接相加当作总 p95。

**工程取舍：**售后助手先识别问题类型：政策问答走 RAG；订单状态走只读 API；退款走固定业务流程。模型不能确定订单号时让用户选择，不能模糊匹配后直接写入。上线实验同时记录正确率、拒答率、成本和延迟，避免通过大量拒答“优化”错误率。

## 常见误区与过关标准

- 误区：temperature=0 就是确定性程序；上下文容量等于有效记忆；向量相似度等于事实置信度；DTO 成功转换等于业务有效。
- 练习：画出“输入 → 模型 → 工具 → 校验 → 响应”，标注身份、超时、截断、失败与成本位置。参考验证：任何有副作用的箭头前都应有服务端授权与领域校验，任何失败都有显式状态。
- L1 过关：2 分钟说明 token、context、embedding、结构化输出的区别。
- L2 过关：手算预算，解释 TTFT 与总延迟不同，指出 KV cache 的资源代价。
- L3 过关：完成上述 7 题及追问，能给每个优化提出质量验证方法。
- L4 过关：设计一次模型替换实验，列出版本锁定、分桶、回滚与业务成功率口径。
