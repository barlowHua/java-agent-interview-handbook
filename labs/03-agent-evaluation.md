# 实验 03｜不需要 API key 的 Agent 评测与副作用验证

目标：把“回答挺好”变成能复核的指标，亲手看到检索命中、证据支持、回答正确、业务成功之间的差别。前置：[RAG](../modules/16-rag.md)、[Agent 架构](../modules/17-agent-architecture.md)、[生产工程](../modules/18-agent-production.md)。预计 60～90 分钟。

本实验用 Python 3.9+ 标准库运行，不安装依赖、不访问网络、不读取真实订单、不执行支付或真实写操作。核心技能是评测设计，Java 工程师可以把同一指标和测试数据迁移成 JUnit。**这是规则与固定样本的模拟，不是实际 LLM、embedding、重排模型或生产安全评测。**

## 1. 运行

在项目根目录执行：

```bash
python3 labs/agent_eval_demo.py --self-test
```

查看逐题明细：

```bash
python3 labs/agent_eval_demo.py --self-test --json
```

源代码：[agent_eval_demo.py](agent_eval_demo.py)。脚本输出到终端，不修改数据文件。核对日期：2026-10-04，本版脚本已在本地实际执行并通过内置断言。

## 2. 先理解实验边界

样本库包含七篇模拟文档、两个模拟订单和八个任务。每题提供预先排好的候选文档 ID，**这代替真实检索服务，不是在实现向量检索**。生成器把文档中的原子事实 ID 原样组成回答，**这代替真实语言生成，不能测量自然语言推理能力**。路由器只有两个关键词规则，也不代表真实意图识别。

`expected_*` 是只在评分器读取的金标准。运行链路读取用户输入、候选结果和模拟服务，不读取答案标签。这样可以学习“被测系统”和“评分规则”分离；但固定样本很小，改进方案也是针对已知教学故障设计的，因此全通过不能推出泛化能力。

两个模式的差别：

| 位置 | baseline：故意保留的缺陷 | improved：教学修复 |
|---|---|---|
| 检索 | 直接取候选前两条 | 按租户与有效性过滤，再取前两条 |
| 无证据 | 生成固定的虚构默认答案 | 显式拒答 |
| 订单路由 | 把状态查询发往 RAG | 按关键词进入只读订单工具 |
| 退款 | 缺少授权校验，重复请求重复生效 | 对象归属校验、稳定幂等键、参数冲突校验 |

这里的租户字符串就是简化认证上下文，不是完整 RBAC/ABAC。真实系统还要验证组成员、对象共享、权限撤销、凭据范围、并发与缓存。

## 3. 八个任务分别测什么

| 样本 ID | 故障场景 | 合格行为 |
|---|---|---|
| policy | 旧退款制度与其他租户文档排在前面 | 检索到当前规则和例外，不暴露其他租户资料 |
| leave | 普通可回答题 | 从授权文档正确回答 |
| acl | 用户请求别的租户内部预算 | 拒绝，未授权文档不进入生成输入 |
| no_answer | 问不存在的火星差旅制度 | 拒答，不编造制度 |
| order | 查询订单状态 | 路由权威业务 API |
| refund | 结果丢失后同一个退款意图被重放 | 返回已有结果，副作用总数为 1 |
| refund_acl | 请求退款他人订单 | 拒绝，副作用为 0 |
| freshness | 旧差旅标准与新标准一起命中 | 只使用当前有效证据 |

退款服务是内存计数器。脚本先调用一次，再模拟“响应丢失后的重复交付”；不模拟网络超时、进程真实崩溃或并发，因此仅证明顺序重放的特定规则。

## 4. 预期结果与手算

```text
指标                             baseline  improved
Recall@2                         0.667     1.000
Hit@2                            0.667     1.000
MRR@2                            0.500     1.000
grounded_fixture_claim_rate      0.750     1.000
route_accuracy                   0.875     1.000
answer_accuracy                  0.250     1.000
correct_refusal_rate             0.000     1.000
business_success_rate            0.125     1.000
unauthorized_document_exposures   2         0
```

Recall 只统计三个有相关文档的 RAG 题：policy、leave、freshness。baseline 的 Recall 分别为 0、1、1，宏平均为 2/3。freshness 虽然检索到了正确文档，生成时同时使用旧制度，仍然业务失败；这证明“找到了”不等于“答对了”。

MRR 对三个题分别是 0、1、1/2，平均为 0.5。本实验只观察前两条，所以严格名称是 MRR@2。无答案与无权限的两个 RAG 题不参加 Recall 分母，单独计算正确拒答率。实际项目还需区分资料确实不存在与存在但未授权，两者给用户的提示不能泄露敏感信息。

grounded_fixture_claim_rate 只在实际走 RAG 且产生事实的样本上按断言微平均。baseline 生成八条原子事实，其中六条可以在其上下文中找到，因此为 6/8。它允许“被旧制度支持”和“被越权文档支持”的事实计为受证据支持；**这只是指标定义的结果，不是对正确性与权限的认可。**

baseline 的 `refund` 返回正确的 `refund_accepted`，所以答案正确，但副作用发生两次，业务失败。因此答案正确率是 2/8，业务成功率只有 1/8。此处业务成功同时要求路由正确、事实和拒答状态正确、无越权文档、副作用次数符合期望。

拒答不包含断言，不能把空回答的 groundedness 自动算成 100%。脚本在没有可评分断言时返回 `null`，而不是编造一个比例。业务成功另行判断是否完成应该完成的任务。

## 5. 动手修改：先预测，再运行

### 练习 A：让 Recall 与权限相互影响

在 `policy` 的候选最前面再插入一个不可见文档，并先取 top2 后过滤。预测结果与改进版有何不同。

**参考答案：**如果前两条均不可用，过滤后没有证据，尽管合法证据排在后面，Recall 仍为 0。应在可信边界内先施加权限约束，或由检索引擎扩大候选并持续扫描，同时保证未授权内容从未发送给模型或外部重排服务。不能为追求 Recall 放松权限。

### 练习 B：加入不完整证据

让 `policy` 只返回 `refund_current`，仍要求答案包含例外 `opened_goods_excluded`。

**参考答案：**Recall=1/2、Hit=1，已生成断言的支持率可能仍为 1，但答案不完整、业务应失败。如果只看 Hit 或 groundedness，会遗漏必要条件。把“关键条件完整率”作为独立诊断也有价值。

### 练习 C：制造重复动作

将 `intent_id` 改成每次调用新生成的值，再执行同一业务意图两次。

**参考答案：**即使服务支持幂等，不同键也会被当作两次动作，副作用变为 2。幂等键必须在重试、进程恢复和调用链中稳定绑定业务意图。相同键但不同订单或金额应拒绝，而不是返回不相关的旧结果。

### 练习 D：增加一个新表达

增加“这笔订单现在到哪一步了”的样本，期望路由订单工具，但输入不含“订单状态”。

**参考答案：**improved 关键词规则可能失败。这个反例直接说明 fixture 全通过并不代表自然语言泛化。可引入更多规则或模型分类，但必须重新测路由准确率、低置信处理、成本和错误升级机制，不能只把这个句子硬编码进去后宣布解决。

### 练习 E：设计真实崩溃恢复

只画设计，不调用外部服务：动作成功后、本地状态保存前进程退出，重启如何避免重复退款？

**参考答案：**先持久化意图和稳定键；服务端持久化幂等结果；恢复 worker 查询该键的业务状态并补记结果，暂时无法确认则保留 UNKNOWN。内存字典重启会丢失，所以不能把本实验直接当作持久化方案。并发还需要唯一约束、事务或原子幂等存储，单纯先查后写会有竞争。

## 6. 换成真实模型时必须补什么

保留评分入口，用真实检索输出替换候选 fixture，用真实模型输出替换事实 ID 生成器。记录模型、prompt、schema 和索引版本；增加人工标注的必要事实与证据范围。引用与数字用程序核对，开放文本采用经过人工校准的裁判。模型裁判输入本身也要视为不可信，不应拥有业务写权限。

准备独立测试集，覆盖同义表达、多轮、省略、歧义、跨租户、无答案、注入、工具超时和取消；对随机模型重复运行，报告每类表现和波动。把任务延迟、token、工具成本及人工接手加入结果。实际写工具先用可回滚的测试环境，影子评测不重复执行真实副作用。

## 7. 验收与面试表达

- 基础：能不看代码算出 2/3 的 Recall 与 0.5 的 MRR，讲清分母。
- 进阶：能解释 groundedness 很高却使用了旧制度，以及“退款成功”文字正确却重复退款。
- 工程：能指出内存幂等缺少持久化和并发保障、关键词路由没有语义泛化能力。
- 面试交付：提交一次新增反例的 JSON 输出、指标变化解释，以及真实模型接入的评测设计。

推荐表达：“我做了一个离线评测原型，验证了指标与执行边界，区分检索、答案和业务结果；它不证明实际模型质量。下一步需要接入真实任务与工具，补足持久化、并发、开放文本评分和线上灰度。”不要说“我已经把 Agent 成功率做到 100%”。
